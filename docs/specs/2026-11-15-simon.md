# Simon

15 November 2026

## Summary

Simon is an iPhone messaging app that a household runs for itself on its own machine. Each chat in the app is an agent. You send it a message, it does the work, and a finished reply arrives like a text from a person. The agent runs on a machine we own, using Claude Code, and each person's usage counts against their own Claude subscription.

Hosted products such as Grok Bot do this for $30 to $200 a month per person and keep the data on their servers. Simon reuses the Claude subscriptions we already pay for, plus the skills and connections Claude Code already has.

## Decisions

- **Each household runs its own Simon.** The code is open source. Every agent on a server runs as the same user account on that machine and can reach that account's files, so a server is shared only by people who trust each other with that machine. Anyone else runs their own server and builds their own copy of the app.
- **Nothing personal is in the code.** The people, their Tailscale logins and their Claude config folders live in `~/.simon`. The app asks for its server's address on first launch. The Apple team and app identifier come from `mobile/.env.local`, which is not committed.
- **Two programs.** A server written in TypeScript on Node, and a phone app written in TypeScript with React Native and Expo. React Native draws real native views, and the same code can build an Android app later. The app imports the server's wire types from `server/src/contract.ts`, so the two can't drift apart. There is no web or Mac client.
- **The server runs on the MacBook,** as a service macOS starts at login and restarts if it stops. It can move to any machine that runs Claude Code by copying `~/.simon` and signing in to Claude Code there.
- **Claude Code does the agent work.** The server drives it through the Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`). The SDK starts the Claude Code program, which is already signed in.
- **Each person uses their own Claude login.** Each person has their own Claude Code config folder, and the server sets `CLAUDE_CONFIG_DIR` to that folder for every run that person triggers. Simon never reads, stores or passes on a login. Anthropic's terms require each person to sign in themselves through Anthropic's own sign-in.
- **A chat and a session are different things.** A chat is the endless list of messages a person sees, stored by Simon. A session is what the model reads, stored by Claude Code. An agent has one chat for its whole life and one current session that gets replaced when it grows large. A session that never ends gets slower, less accurate, and uses more of the subscription per message, because the model rereads all of it on every turn.
- **Only finished replies are messages.** Tool calls and the agent's working steps stay in Claude Code's session file. They are never stored in Simon or shown in the app.
- **An agent belongs to one person.** Two people never share a chat, so it is always clear whose subscription a reply uses. Shared information lives in Notion.
- **Each agent has a home folder.** The agent runs there. The folder holds its instructions, its memory and the attachments sent to it.
- **Memory is Claude Code's own.** Claude Code already keeps notes between sessions: a `MEMORY.md` list it reads at the start of each session, and one file per thing it has learned. Simon points that feature at the agent's `memory/` folder, so what an agent learns outlives every session and moves with `~/.simon`. It is on for Simon's agents even when their owner has turned it off for their own Claude Code.
- **Each agent has its own model and effort.** A new agent starts on Opus at medium effort. The person picks from Fable, Opus, Sonnet and Haiku, by the names Claude Code gives them, so each always means the newest model of its kind, and from low, medium and high effort. Simon has no other model settings.
- **Each agent keeps its own instructions and memory.** Simon gives every agent the same few starting lines and no shared rules after that.
- **Jobs run by Simon's own clock.** Claude Code's own scheduled tasks only fire while a session is open, and its cloud ones can't reach this machine's files. Simon runs one call per turn, so the server keeps the schedule and starts each run itself.
- **Agents run in Claude Code's auto mode.** Claude Code checks each action with its own safety classifier and runs the ones it judges safe. Simon adds no restrictions and has no approval step.
- **Agents load their owner's Claude Code setup.** Whatever global rules, skills and connections that person has in Claude Code on the server machine apply to their Simon agents too.
- **Simon data lives in `~/.simon`,** separate from the code. Messages live in one SQLite file, the same approach T3 Code takes with `statev2.sqlite`.
- **The phone reaches the server over Tailscale.** The server listens on the local machine only, and `tailscale serve` publishes it over HTTPS to our own devices. Nothing is open to the public internet.
- **Tailscale tells the server who is asking.** `tailscale serve` adds the sender's Tailscale login to each request, and the server matches it to a person. Simon has no passwords or sign-in screen of its own.
- **The server is the source of truth.** The app keeps a local copy of messages so chats open instantly and work offline, and it refills that copy from the server.
- **Every agent is a pet.** A pet is an animated pixel character that acts out what its agent is doing.
- **People make their own pets by asking an agent.** Claude can't paint images, but it can write pixel art as a grid of letters. Simon's `hatch-pet` skill has the agent draw the pet once as a 16 by 16 grid, and a script turns that grid into every animation frame. Every pet moves the same way and the whole thing runs on Claude.
- **The app installs through TestFlight,** built with the Apple Developer account of the person who runs the server. The server sends notifications with that account's push key.

## Behavior

**First launch.** The app asks for the server's Tailscale address and remembers it.

**Home.** The app opens on the person's agents, each with its pet, its name and its latest message. There is no title bar and no heading. A glass search field floats at the top. Typing in it lists the agents whose name matches, then the messages that contain the words, from every chat. A tap on either opens that chat. An agent with replies the person hasn't read shows how many, in a round count at the end of its row. The button for a new agent floats at the bottom right, where a thumb reaches it. A swipe left on an agent shows Mute, Hide and Delete. A muted agent sends no notifications, stays out of the count on the app's icon, and shows a small crossed bell by its name. A hidden agent leaves the list and waits under a "Hidden" line at its end, which a tap opens. It comes back by itself when it next has something to say, unless it is muted. Search finds hidden agents too.

**Chat.** Opening an agent shows the full message history. Nothing in the chat is a bar: a glass back button, the agent's pet with its name in a pill, and the message field all float over the messages, which scroll behind them. The person sends text, photos or files. The + in the message field opens a menu of Photos, Camera and Files, as Assist's does. Camera opens full screen with a quick fade and takes photos one after another, each joining a row under the preview, and Add puts them all in the message. What they pick sits in a row of tiles above the text until it is sent, up to ten to a message. A sent message shows straight away, faded until the server has it. In the chat, one photo shows in its own shape and several show as square tiles. A tap opens them full screen, to swipe between, pinch and share. A file shows as a card with its kind and opens in the share sheet. While the agent works, its pet plays its working animation beside a short playful line that changes every few seconds. The line says nothing about what the agent is doing. The reply arrives as one message. A swipe right on any message replies to it: the message is quoted above the field until it is sent or let go, the sent message shows the quote at the top of its bubble, and the agent is told which message it answers. While the message field is open it names the agent's model and effort beside the +, and a tap on them opens one menu that changes either. The new choice shows the moment it is tapped. Scrolling up to the oldest message on the phone fetches the ones before it. A tap on the agent's pet or name opens its page.

**Agent page.** The page shows the agent's pet and name, which can both be changed there, its model and effort, and switches for Mute and Hide. Below them is what the agent works from: its jobs, each with when it runs, when it next runs and what it does, and a button to remove it; the instructions it follows; and what it remembers. Instructions and memories open to read in full. The agent writes all three itself, as the person tells it things in the chat. The page ends with Delete.

**Jobs.** The person asks an agent, in its chat, to remind them of something or to keep an eye on something, and the agent saves a job: once at a time, at a time of day on every day or on chosen weekdays, or every so many minutes. Simon runs the job when its time comes. If the run finds something worth telling, it arrives as a message from the agent with a notification. Otherwise nothing shows. An agent can list and remove its own jobs when asked, and the person can remove one from the agent's page.

**Deleting an agent.** Delete asks first, since nothing comes back. It removes the agent's chat, its jobs, its home folder with its instructions, memory and attachments, and the sessions Claude Code kept for it. A turn it is running is stopped.

**Away from the app.** The agent keeps working after the phone is locked or the app is closed. When the reply is ready, or the turn fails, the phone shows a notification with the agent's name over what it said, with Simon's own soft two-note sound. Tapping it opens that chat. The app's icon shows how many replies are unread across all agents. The app asks to send notifications the first time the person sends a message. While the app is open no notification shows or sounds, since the chat list already has the counts.

**Sending while the agent is busy.** The message is saved and shown straight away. The agent handles messages in the order they were sent, one turn at a time.

**New agent.** The person taps the plus button on the home screen, gives the agent a name and picks a pet from the ones on the server. Its chat opens straight away. The server creates its home folder with a standard set of instructions, and the agent adds to them as the person tells it what it is for.

**Pets.** A pet shows the agent's state wherever the agent appears: resting, working, a reply waiting, or a failed turn. When the server can't be reached, every pet shows its resting pose, greyed out.

**Hatching a pet.** The person asks any agent for a new pet, describing it or sending a photo. The agent makes it and replies when it's ready, and the pet appears in the picker for new agents. Any agent's pet can be changed from its page.

**Fresh start.** A command in the chat's menu, behind the glass button at the top right, replaces the current session. The messages on screen stay as they are, and a "Fresh start" line marks the place in the chat. The agent first writes what is worth keeping into its memory. A session that grows large gets a fresh start by itself.

**Actions that change things.** The agent acts without asking. When auto mode blocks an action, the agent says so in its reply and carries on with the rest of the work.

**When something fails.** If a turn fails, the chat shows a short message from Simon saying why, for example that the subscription's usage limit is reached or that Claude Code is signed out on the server. The person's message is kept and can be sent again.

**When the server can't be reached.** The app shows the saved chats, with every pet greyed out. Messages typed in the meantime wait on the phone and send when the connection returns. A change to an agent, such as its model, a mute or a hide, shows at once whether or not the server can be reached. It waits on the phone and goes when the connection returns, and only a change the server refuses is undone.

## Design

### Data folder

```
~/.simon/
  simon.sqlite
  push.json            the key for sending notifications
  agents/
    <agent-id>/
      CLAUDE.md        who the agent is and how it behaves
      memory/          what it has learned, kept by Claude Code
      attachments/     files the person sent
  pets/
    <pet-id>/
      design.json      the pet drawn as a 16 by 16 grid
      pet.json         id, display name, description, spritesheet path
      spritesheet.png
```

### Database

```sql
create table people (
  id                text primary key,
  name              text not null,
  tailscale_login   text not null unique,
  claude_config_dir text not null
);

create table agents (
  id          text primary key,
  person_id   text not null references people(id),
  name        text not null,
  pet_id      text not null,     -- folder name under ~/.simon/pets
  model       text not null default 'opus',  -- Claude Code's name for the model it runs on
  effort      text not null default 'medium',  -- low, medium or high
  muted       integer not null default 0,    -- 1 sends no notifications
  hidden      integer not null default 0,    -- 1 keeps it off the home screen
  session_id  text,              -- current Claude Code session, null before the first turn
  read_at     integer not null default 0,  -- the person has read the chat up to here
  created_at  integer not null
);

create table messages (
  id          text primary key,
  agent_id    text not null references agents(id),
  sender      text not null check (sender in ('person', 'agent', 'simon')),
  body        text not null,
  attachments text not null default '[]',  -- JSON list of paths inside the agent's home folder
  status      text not null check (status in ('queued', 'running', 'done', 'failed')),
  reply_to    text,              -- the message this one answers
  job_id      text,              -- the job whose run sent it
  created_at  integer not null
);

create table jobs (
  id          text primary key,
  agent_id    text not null references agents(id),
  what        text not null,     -- the agent's instructions to itself for a run
  schedule    text not null,     -- JSON: {type: "every", minutes} or {type: "daily", time, weekdays?} or {type: "once", at}
  next_at     integer not null,  -- when it next runs
  created_at  integer not null
);

create table devices (
  push_token  text primary key,  -- the phone's Apple device token
  person_id   text not null references people(id),
  topic       text not null,     -- the app identifier Apple delivers to
  environment text not null check (environment in ('sandbox', 'production'))
);
```

`sender = 'simon'` marks messages the server writes itself: failure notices and fresh starts. For a message from a person, `status` tracks the turn it started. A fresh start goes through the same states while the session is replaced. A failure notice is `failed`.

A column added to a table after the first database reaches older databases through a list of `alter table` statements in the store. SQLite's `user_version` counts how many a database has had.

### Server modules

- **store** owns the database and the agent folders. Nothing else touches SQLite or `~/.simon`.
- **runner** runs one turn. It is the only module that imports the Agent SDK.
- **api** owns the HTTP routes and the live event stream, and works out which person is asking.
- **push** sends notifications through Apple's push service.

### Keeping the server running

On a Mac, a launchd agent in `~/Library/LaunchAgents` runs `node src/main.ts` in the `server` folder, with `RunAtLoad` and `KeepAlive` set, and its output goes to `~/.simon/server.log`. macOS doesn't let a background service read `~/Downloads`, `~/Documents` or `~/Desktop`, so the code lives outside them.

### Pets

A pet's spritesheet is one image with a grid of 8 columns and 4 rows, each cell 192 by 208 pixels. Each row is one animation and each cell in it is one frame. The app animates a pet by showing one cell at a time from the row it wants.

| Row | State | Frames | Shown when |
| --- | --- | --- | --- |
| 0 | `resting` | 6 | Nothing is happening, and greyed out when the server can't be reached |
| 1 | `working` | 6 | The agent is running a turn |
| 2 | `replied` | 6 | A reply the person hasn't opened |
| 3 | `failed` | 8 | The last turn failed |

`skills/hatch-pet/render.ts` builds every frame from the pet's `design.json`. Each row applies the same changes to the one grid: eyes open, blinking, looking down, happy or crossed, a hop, a heart or a sweat drop, and grey colours for `failed`. The agent writes `design.json` into `~/.simon/pets/<pet-id>/`, runs the script, and looks at the result before replying.

The starter pets live in the repository's `pets/` folder and are copied into `~/.simon/pets` on the server's first start.

### Adding a person

The person who runs the server adds each person once, with their Tailscale login, their name and their Claude Code config folder: `pnpm add-person <tailscale-login> <name> <claude-config-dir>`. That person signs in to Claude Code in that config folder themselves.

### Running a turn

For each queued message, the runner calls the SDK's `query` once with:

- `cwd` set to the agent's home folder
- `resume` set to the agent's `session_id`, when it has one
- `env` carrying `CLAUDE_CONFIG_DIR` for the person who owns the agent
- `settingSources` of `user` and `project`, so the person's skills and connections load along with the agent's `CLAUDE.md`
- `systemPrompt` set to the `claude_code` preset, which is Claude Code's full prompt. Without it the SDK uses a short one that leaves out memory
- `settings` that turn Claude Code's memory on and set its folder to the agent's `memory/`
- `skills: 'all'`
- `permissionMode: 'auto'`
- `model` and `effort` set to the agent's
- `abortController`, which stops the turn if its agent is deleted

Files sent with a message are saved in the agent's `attachments/` folder before the turn, and the prompt ends with their paths. The agent opens them with its ordinary file tools.

The runner takes the reply text and the session ID from the SDK's result message, saves the reply as a message, and stores the session ID on the agent. One call per message keeps the server free of long-lived state, so a restart loses nothing. Each agent runs one turn at a time.

When a message answers an earlier one, the prompt starts by quoting it.

### Jobs

The runner gives each agent three tools beside `search_history`: `schedule_job`, `list_jobs` and `cancel_job`. A job is what to do on each run, written by the agent to itself, and a schedule. Times are the server machine's local time, and the tools' answers tell the agent the time now.

A clock in the server looks every 15 seconds for jobs whose time has come and starts their agents' queues. An agent's queue runs the messages it was sent first, then any job that is due, one turn at a time, so a job never runs alongside a reply in the same folder.

A job's run is a new session that is not saved (`persistSession: false`), on the agent's model, in the agent's folder. It never touches the chat's session, so a job that runs every few minutes doesn't fill it. The prompt gives the run the job's instructions, tells it to keep what the next run needs in memory, and tells it to reply with only the word `SILENT` when there is nothing worth telling. Any other reply is saved as a message from the agent, with the job's id, and notifies the phone. The chat's session never saw that message, so the person's next message carries what the jobs sent since the agent's last reply.

After a run, an interval counts from the end of the run, a daily job moves to its next day, and a job set for one time is removed. After the machine has been asleep or off, each job that was due runs once. A run that fails adds a failure notice to the chat, unless the latest message there is already one.

### Replacing a session

A session is replaced when the person asks for a fresh start, or when a turn ends with the session holding more than 120,000 tokens. The size comes from the usage on the agent's last step, which counts everything the model read for it.

A fresh start is a message from Simon that waits in the agent's queue like any other, so it runs after the turns ahead of it. The runner first runs one turn asking the agent to save what is worth keeping to its memory, and then clears `session_id`. If that turn fails the session is replaced anyway, since the chat is still there to search. The next turn starts a new session whose first prompt includes the 20 most recent messages from the database.

### Looking at past messages

One search in the store finds the messages that contain a word or phrase, across all agents that belong to the same person, newest first. The runner gives it to each agent as a `search_history` tool, built with the SDK's `createSdkMcpServer` and `tool`. The app's search field reaches it through `GET /search`.

### Notifications

The server sends notifications straight to Apple's push service, signed with the push key of the Apple Developer account that built the app. The person who runs the server creates the key once at developer.apple.com and saves it with `pnpm push-key <AuthKey_XXXXXXXXXX.p8> <apple-team-id>`. Until then notifications are off and everything else works.

The app gives the server its device token once the person allows notifications, and again on each return to the app. The server sends a notification when an agent's reply is saved and when a turn fails, unless the agent is muted. Each one carries the number of replies and failure notices the person hasn't read across their agents that aren't muted, which the app's icon shows, and the sound `simon.wav`, which the app carries in its bundle. When Apple says a token is no longer in use, the server forgets that phone.

An agent's unread count is its replies and failure notices newer than its `read_at`. Opening a chat sets `read_at` through `POST /agents/:id/read`, which clears the count on every phone.

### API

| Route | Purpose |
| --- | --- |
| `GET /agents` | The person's agents with their latest message and unread count |
| `POST /agents` | Create an agent |
| `PATCH /agents/:id` | Change an agent's name, pet, model or effort, or whether it is muted or hidden |
| `DELETE /agents/:id` | Remove an agent and everything it had |
| `GET /agents/:id/about` | The agent's instructions, memories and jobs |
| `DELETE /agents/:id/jobs/:job` | Remove one of the agent's jobs |
| `GET /agents/:id/messages?after=<message-id>` | The newest page of messages, everything after a known message, or with `before=<message-id>` the page before one |
| `POST /agents/:id/messages` | Send a message, as a form with `body`, any `files`, and `replyTo` for the message it answers. Text alone can be JSON |
| `GET /agents/:id/attachments/:name` | A file that was sent with a message |
| `POST /agents/:id/read` | Mark the chat read up to now |
| `POST /agents/:id/fresh-start` | Replace the current session |
| `GET /search?text=<words>` | The messages that contain the words, in any of the person's chats |
| `GET /pets` | The pets on the server |
| `GET /pets/:id/spritesheet` | A pet's spritesheet |
| `POST /devices` | Register a phone for notifications |
| `GET /events` | Live stream, as server-sent events. Each event is a message that was added or changed status, with its agent as the home screen shows it |

Every route reads the Tailscale login from the request and only returns that person's agents and messages.

### Phone app

The app lives in `mobile/` and uses Expo Router, where each file under `src/app` is a screen. It has four screens and three sheets: server setup, home, the chat and the camera, and the sheets for a new agent, an agent's page, and a note opened from that page. Photos come from `expo-image-picker`, the camera from `expo-camera`, files from `expo-document-picker`, and notifications from `expo-notifications`. The + menu, the model menu and the chat's menu are the system's own menus, drawn by a small native module in `mobile/modules/message-menu` copied from Assist: a clear iOS menu button laid over what the person taps. The swipes on a row of the home screen and on a message come from `react-native-gesture-handler`. The keyboard moves the message field through `react-native-keyboard-controller`, which follows the keyboard on the UI thread, frame by frame. The playful lines shown while an agent works are a list inside the app. A pet view takes a spritesheet and a row and draws the frames in turn, and the app caches spritesheets on the phone. The app keeps a local copy of agents, messages, what each opened agent page showed, and the changes to agents the server doesn't have yet in Expo's SQLite key-value store. Those changes are laid over whatever the server sends until the server has them, so a reply arriving mid-change can't undo one. While open, it listens to `GET /events`. On launch and on returning to the foreground, it reconnects and fetches the newest page of each chat it has opened.

## Testing

The server is tested through its HTTP routes, with the runner swapped for a fake that returns set replies. That covers ordering, queuing, failure messages and the per-person filter without spending subscription usage. One manual check per slice runs a real turn through Claude Code. The app is checked in the iOS Simulator and then on a phone over Tailscale.

## Out of scope

- Live voice
- Chats shared between two people
- One build of the app shared by several households
- Agents that talk to other people's agents
- A Simon sign-in of its own, such as Google sign-in
- An Android build, and any client other than the phone app
- Driving websites that need a typed password
- Moving the server off the MacBook

## Open questions

- **Which service powers live voice?** Not needed until voice is in scope.

## Work breakdown

Each slice ends with something that works on its own.

1. **One agent, no app.** Server, database, one agent folder, and the runner. Sending a message with `curl` returns a reply. This proves the subscription login, skills, connections and auto mode work through the SDK.
2. **Chat on the phone.** The server setup screen, the chat screen, the event stream, and Tailscale. A message typed on the iPhone gets a reply from the agent on the MacBook.
3. **Many agents.** The home screen, creating an agent from the plus button, pets and the pet picker, and identifying the person from their Tailscale login.
4. **Notifications.** Device registration and a notification when a reply lands.
5. **Attachments.** Sending a photo or file into the agent's folder.
6. **Memory and fresh start.** Memory files, replacing a session by hand and by size, and `search_history`.
7. **Hatching pets.** An agent makes a new pet with the `hatch-pet` skill.
8. **Agents you can manage.** Jobs, the agent page, the model and effort, mute, hide and delete, replies to a message, and older messages.
9. **Second person.** A second config folder and Claude login on the server, a second Tailscale user, and the TestFlight build on both phones.
