# Sidebots

15 November 2026

## Summary

Sidebots is an iPhone messaging app that a household runs for itself on its own machine. Each chat in the app is an agent. You send it a message, it does the work, and a finished reply arrives like a text from a person. The agent runs on a machine we own, using Claude Code, and each person pays for their own agents' usage, on their Claude subscription or on an Anthropic API key.

Hosted products such as Grok Bot do this for $30 to $200 a month per person and keep the data on their servers. Sidebots reuses the Claude subscriptions we already pay for, plus the skills and connections Claude Code already has.

## Decisions

- **Each household runs its own Sidebots.** The code is open source. Every agent on a server runs as the same user account on that machine and can reach that account's files, so a server is shared only by people who trust each other with that machine. Anyone else runs their own server and builds their own copy of the app.
- **Nothing personal is in the code.** The people, their paired phones, their Claude config folders and their API keys live in `~/.sidebots`. The app pairs with its server on first launch. The Apple team and app identifier come from `mobile/.env.local`, which is not committed.
- **Two programs.** A server written in TypeScript on Node, and a phone app written in TypeScript with React Native and Expo. React Native draws real native views, and the same code can build an Android app later. The app imports the server's wire types from `server/src/contract.ts`, so the two can't drift apart. There is no web client. The Mac app in `mac/` holds the server and shows no chats.
- **The server runs on the MacBook,** as a service macOS starts at login and restarts if it stops. It can move to any machine that runs Claude Code by copying `~/.sidebots` and, for each person who uses a Claude login, signing in to Claude Code there.
- **Claude Code does the agent work.** The server drives it through the Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`). The SDK starts the Claude Code program, which runs each turn on its owner's Claude login or API key.
- **Each person pays for their own agents, with a Claude login or an API key.** Each person has their own Claude Code config folder, and the server sets `CLAUDE_CONFIG_DIR` to that folder for every run that person triggers. Claude Code keeps the person's sessions there and loads their rules, skills and connections from it. With a Claude login, the person signs in to Claude Code in that folder themselves, through Anthropic's own sign-in, and their agents use their subscription. Sidebots never reads, stores or passes on a login. With an Anthropic API key, the person who runs the server saves the key in `~/.sidebots`, the server hands it to Claude Code for every run that person triggers, and Anthropic bills the key's account. A person with a key needs no sign-in.
- **Anthropic's terms decide which of the two a person may use.** A subscription is for the subscriber's own use, so a household that runs Sidebots for itself can use its own logins, each person signing in themselves. For a product built on the Agent SDK, Anthropic asks for API keys and doesn't allow Claude logins to be offered to the product's users without its approval. So anyone who sets Sidebots up for other people reads the terms first and, when in doubt, gives each of them a key.
- **A chat and a session are different things.** A chat is the endless list of messages a person sees, stored by Sidebots. A session is what the model reads, stored by Claude Code. An agent has one chat for its whole life and one current session that gets replaced when it grows large. A session that never ends gets slower, less accurate, and costs more per message, because the model rereads all of it on every turn.
- **Only replies and the agent's own updates are messages.** Tool calls and the agent's working steps stay in Claude Code's session file. They are never stored in Sidebots or shown in the app. During long work the agent may send a short update of its own choosing.
- **An agent belongs to one person.** Two people never share a chat, so it is always clear whose subscription or API key a reply uses. Shared information lives in Notion.
- **Each agent has a home folder.** The agent runs there. The folder holds its instructions, its memory and the attachments sent to it.
- **Memory is Claude Code's own.** Claude Code already keeps notes between sessions: a `MEMORY.md` list it reads at the start of each session, and one file per thing it has learned. Sidebots points that feature at the agent's `memory/` folder, so what an agent learns outlives every session and moves with `~/.sidebots`. It is on for Sidebots' agents even when their owner has turned it off for their own Claude Code.
- **Each agent has its own model and effort.** A new agent starts on Opus at medium effort. The person picks from Fable, Opus, Sonnet and Haiku, by the names Claude Code gives them, so each always means the newest model of its kind, and from low, medium and high effort. Sidebots has no other model settings.
- **Each agent keeps its own instructions and memory.** Sidebots gives every agent the same few starting lines and no shared rules after that.
- **Jobs run by Sidebots' own clock.** Claude Code's own scheduled tasks only fire while a session is open, and its cloud ones can't reach this machine's files. Sidebots runs one call per turn, so the server keeps the schedule and starts each run itself.
- **Agents run in Claude Code's auto mode.** Claude Code checks each action with its own safety classifier and runs the ones it judges safe. Sidebots adds no restrictions and has no approval step.
- **Agents load their owner's Claude Code setup.** Whatever global rules, skills and connections that person has in their Claude Code config folder apply to their Sidebots agents too. Connectors the person added on claude.ai come only with a Claude login.
- **Sidebots data lives in `~/.sidebots`,** separate from the code. Messages live in one SQLite file, the same approach T3 Code takes with `statev2.sqlite`.
- **The phone reaches the server over Tailscale.** The server listens on the local machine only, and `tailscale serve` publishes it over HTTPS to our own devices. Nothing is open to the public internet.
- **Pairing tells the server who is asking.** The server makes a one-time code for a person, that person's phone scans it and gets a key of its own, and the server refuses every request without a known key. Sidebots has no accounts, passwords or sign-in screen.
- **The server is the source of truth.** The app keeps a local copy of messages so chats open instantly and work offline, and it refills that copy from the server.
- **Every agent has an avatar.** An avatar is an animated pixel character that acts out what its agent is doing.
- **People make their own avatars by asking an agent.** Claude can't paint images, but it can write pixel art as a grid of letters. Sidebots' `make-avatar` skill has the agent draw the avatar once as a 16 by 16 grid, and a script turns that grid into every animation frame. Every avatar moves the same way and the whole thing runs on Claude.
- **The app installs through TestFlight,** built with the Apple Developer account of the person who runs the server. The server sends notifications through a relay that holds that account's push key.

## Behavior

**First launch.** The app opens on a welcome screen: the app's icon, one line on what Sidebots is, and the two steps to pair, getting Sidebots for Mac from sidebots.app and scanning the code it shows. Its one button, "Scan the code", opens the camera, and only then does the phone ask for the camera. The camera is laid out as the chat's camera: the preview on black, with one line under it asking for the code the server made for the person, and a back button above it. If the person refused the camera, a button in its place opens Settings. Scanning the code pairs the phone, the line names the machine it paired with, and the app opens on the agents. A link button above the preview asks for the same code as its link, in the system's own prompt, and a pairing link opened anywhere on the phone pairs it too. A code works once, for ten minutes. A phone the server doesn't know goes back to the welcome screen, with its saved chats cleared and a line saying the Mac removed it. The line stays, through relaunches, until the phone pairs again.

**Home.** The app opens on the person's agents, each with its avatar, its name and its latest message. There is no title bar and no heading. A glass button for a new agent floats at the top right. A glass search field floats at the bottom, where a thumb reaches it, and rises with the keyboard. Typing in it lists the agents whose name matches, then the messages that contain the words, from every chat. A tap on either opens that chat. An agent with replies the person hasn't read shows how many, in a round count at the end of its row. A person with no agents yet sees "No agents yet" with a line pointing at the + button, and no search field. A swipe left on an agent shows Mute, Hide and Delete. A muted agent sends no notifications, stays out of the count on the app's icon, and shows a small crossed bell by its name. A hidden agent leaves the list and waits under a "Hidden" line at its end, which a tap opens. It comes back by itself when it next has something to say, unless it is muted. Search finds hidden agents too. An agent the person adds or deletes on another of their phones comes or goes here at once.

**Chat.** Opening an agent shows the full message history. A new agent's chat, until its first message, says "<name> is new. Tell it what it's for." Nothing at the top of the chat is a bar: a glass back button and the agent's avatar with its name in a pill float over the messages, which scroll behind them. The message field sits at the bottom on a strip of the page colour, and opens and rises with the keyboard as Assist's does. The person sends text, photos or files. The + in the message field opens a menu of Photos, Camera and Files, as Assist's does. Camera opens full screen with a quick fade and takes photos one after another, each joining a row under the preview, and Add puts them all in the message. What they pick sits in a row of tiles above the text until it is sent, up to ten to a message. A sent message shows straight away, faded until the server has it. Under the person's newest message a receipt says "Delivered" while it waits for the agent, and "Read" with the time once the agent has taken it in. In the chat, one photo shows in its own shape and several show as square tiles. A tap opens them full screen, to swipe between, pinch and share. A file shows as a card with its kind and opens in the share sheet. While the agent works, its avatar plays its working animation beside a short playful line that changes every few seconds. The line says nothing about what the agent is doing. The reply arrives as one message. The agent's replies show as rich text, as T3 Code shows them: GitHub's markdown, with headings, lists, task lists, quotes, tables, highlighted code and links. The text is selectable. A web link opens in a Safari sheet over the app, and any other link opens the app that handles it. The chat list and notifications show a reply as plain words. A swipe left on any message replies to it, as in Telegram, since a swipe right anywhere in the chat goes back: the message is quoted above the field until it is sent or let go, the sent message shows the quote at the top of its bubble, and the agent is told which message it answers. Scrolling up to the oldest message on the phone fetches the ones before it. What the person has typed stays in the field when they leave the chat and come back. A tap on the agent's avatar or name opens its page.

**Agent page.** The page opens on the agent's avatar, large, with its name and the model and effort it answers with under it. Edit, at the top left, turns the name into a field and brings up the avatars to choose from, and the large avatar changes as one is picked; Save keeps both and Cancel leaves them. Below the avatar are two tabs. Settings holds the model and effort, switches for Mute and Hide, and Delete. Jobs & memory holds what the agent works from: its jobs, each with when it runs, when it next runs and what it does, and a button to remove it; the instructions it follows; and what it remembers. Instructions and memories open to read in full, as rich text, as the agent's replies show. The agent writes all three itself, as the person tells it things in the chat.

**Jobs.** The person asks an agent, in its chat, to remind them of something or to keep an eye on something, and the agent saves a job: once at a time, at a time of day on every day or on chosen weekdays, or every so many minutes. Sidebots runs the job when its time comes. If the run finds something worth telling, it arrives as a message from the agent with a notification. Otherwise nothing shows. An agent can list and remove its own jobs when asked, and the person can remove one from the agent's page.

**Deleting an agent.** Delete asks first, since nothing comes back. It removes the agent's chat, its jobs, its home folder with its instructions, memory and attachments, and the sessions Claude Code kept for it. A turn it is running is stopped.

**Away from the app.** The agent keeps working after the phone is locked or the app is closed. When the reply is ready, or the turn fails, the phone shows a notification with the agent's name over what it said, with Sidebots' own soft two-note sound. Tapping it opens that chat. The app's icon shows how many replies are unread across all agents. The app asks to send notifications the first time the person sends a message. While the app is open no notification shows or sounds, since the chat list already has the counts.

**Sending while the agent is busy.** The message is saved and shown straight away. If the agent is working on the person's earlier message, the new one goes into that turn: the agent reads it at its next pause between steps and answers both in one reply, which steers the work while it is under way. A message sent while the agent runs a job, or replaces its session, waits for its own turn.

**Long work.** When work on a message runs long, the agent may send a short update of where it has got to. It can send the first only after a minute, and then no more than one every three minutes. An update shows in the chat like a reply but arrives quietly: it sends no notification, doesn't count as unread, and doesn't bring a hidden agent back. The final reply does all three. Jobs send no updates. If the agent starts work that runs on in the background, such as a long command, its session stays open for up to half an hour, and when the work finishes the agent picks it up again and sends its result as a new reply.

**New agent.** The person taps the plus button on the home screen, gives the agent a name and picks an avatar from the ones on the server. Its chat opens straight away. The server creates its home folder with a standard set of instructions, and the agent adds to them as the person tells it what it is for.

**Motion.** Nothing on screen snaps into place. A message that comes into an open chat rises into place as it fades in, and the person's own settles from its faded copy where it already sits. The chat the person opens shows as it is. The working line fades in when work starts and out as the reply comes, and its words crossfade as they change. Text that changes, such as a receipt, an agent's latest message on the home screen or a hint, crossfades from the old words to the new. On the home screen, rows slide to their new places as an agent moves up, and fade in and out as they come and go. Unread counts grow in and shrink away. A choice such as the model slides its mark to the new one. Everything follows the phone's Reduce Motion setting.

**Avatars.** An avatar shows the agent's state wherever the agent appears: resting, working, a reply waiting, or a failed turn. When the server can't be reached, every avatar shows its resting pose, greyed out.

**Making an avatar.** The person asks any agent for a new avatar, describing it or sending a photo. The agent makes it and replies when it's ready, and the avatar appears in the picker for new agents. Any agent's avatar can be changed from its page.

**Fresh start.** A command in the chat's menu, behind the glass button at the top right, replaces the current session. The messages on screen stay as they are, and a "Fresh start" line marks the place in the chat. The agent first writes what is worth keeping into its memory. A session that grows large gets a fresh start by itself.

**Actions that change things.** The agent acts without asking. When auto mode blocks an action, the agent says so in its reply and carries on with the rest of the work.

**When something fails.** If a turn fails, the chat shows a short message from Sidebots saying why. The common causes are in plain words with what to do on the Mac: Claude Code is signed out there, the Claude usage limit is reached, with when it resets, or Anthropic refused the API key. Any other failure gives Claude Code's own reason. The notice never shows the key itself. The person's message is kept and can be sent again.

**When the versions don't match.** The app and the server each know which version of their contract they speak. If the server is older, the home screen says "Update Sidebots on your Mac" in place of the agents. If the app is older, it says "Update Sidebots from the App Store". Pairing with a server on another version fails with the same words, and leaves the code unused, so it still pairs once one side is updated. The app keeps asking, and the agents come back once the two match.

**When the server can't be reached.** The app shows the saved chats, with every avatar greyed out. Messages typed in the meantime wait on the phone and send when the connection returns. A change to an agent, such as its model, a mute or a hide, shows at once whether or not the server can be reached. It waits on the phone and goes when the connection returns, and only a change the server refuses is undone.

## Design

### Data folder

```
~/.sidebots/
  sidebots.sqlite
  api-keys.json        the Anthropic API key of each person who uses one
  machine.json         the key that proves this server to the relay, and its id there
  agents/
    <agent-id>/
      CLAUDE.md        who the agent is and how it behaves
      memory/          what it has learned, kept by Claude Code
      attachments/     files the person sent
  avatars/
    <avatar-id>/
      design.json      the avatar drawn as a 16 by 16 grid
      avatar.json      id, display name, description, spritesheet path
      spritesheet.png
```

### Database

```sql
create table people (
  id                text primary key,
  name              text not null unique,  -- what the server's commands call the person
  claude_config_dir text not null
);

create table agents (
  id          text primary key,
  person_id   text not null references people(id),
  name        text not null,
  avatar_id   text not null,     -- folder name under ~/.sidebots/avatars
  model       text not null default 'opus',  -- Claude Code's name for the model it runs on
  effort      text not null default 'medium',  -- low, medium or high
  muted       integer not null default 0,    -- 1 sends no notifications
  hidden      integer not null default 0,    -- 1 keeps it off the home screen
  session_id  text,              -- current Claude Code session, null before the first turn
  read_at     integer not null default 0,  -- the person has read the chat up to here
  created_at  integer not null
);

create table messages (
  id          text primary key,
  agent_id    text not null references agents(id),
  sender      text not null check (sender in ('person', 'agent', 'sidebots')),
  body        text not null,
  attachments text not null default '[]',  -- JSON list of paths inside the agent's home folder
  status      text not null check (status in ('queued', 'running', 'done', 'failed')),
  seen_at     integer,           -- when the agent read a message from the person
  reply_to    text,              -- the message this one answers
  job_id      text,              -- the job whose run sent it
  interim     integer not null default 0,  -- 1 for an update the agent sent while still working
  created_at  integer not null
);

create table jobs (
  id          text primary key,
  agent_id    text not null references agents(id),
  what        text not null,     -- the agent's instructions to itself for a run
  schedule    text not null,     -- JSON: {type: "every", minutes} or {type: "daily", time, weekdays?} or {type: "once", at}
  next_at     integer not null,  -- when it next runs
  created_at  integer not null
);

create table devices (
  id          text primary key,
  person_id   text not null references people(id),
  name        text not null,     -- "Alex's iPhone", as the phone gave it
  key_hash    text not null unique,  -- the hash of the key the phone sends with every request
  notification_key text not null,    -- encrypts this phone's notifications, in base64
  push_token  text,              -- the phone's Apple device token, once it allows notifications
  environment text check (environment in ('sandbox', 'production')),
  paired_at   integer not null
);

create table pairings (
  code_hash  text primary key,   -- the hash of a pairing code that hasn't been used
  person_id  text not null references people(id),
  expires_at integer not null
);
```

`sender = 'sidebots'` marks messages the server writes itself: failure notices and fresh starts. For a message from a person, `status` is `queued` until the agent reads it, `running` once it has, with the time in `seen_at`, then `done` when it has answered, or `failed`. A fresh start goes through the same states while the session is replaced. A failure notice is `failed`.

### Server modules

- **store** owns the database and the agent folders. Nothing else touches SQLite or `~/.sidebots`.
- **runner** runs one turn. It is the only module that imports the Agent SDK.
- **api** owns the HTTP routes and the live event stream, and works out which paired phone is asking and whose it is.
- **push** decides when to notify the person's phones, and what each notification says.
- **relay** sends notifications through the relay. It is the only module that talks to it.

### Keeping the server running

The Mac app in `mac/` keeps the server running: it starts the server as a child process, starts it again when it stops, and opens at login. It learns the server's state only from the server's own commands, as a person at a terminal does. `docs/specs/2026-11-16-published-app.md` describes it.

Without the Mac app, a launchd agent in `~/Library/LaunchAgents` runs `node src/main.ts` in the `server` folder, with `RunAtLoad` and `KeepAlive` set, and its output goes to `~/.sidebots/server.log`. macOS doesn't let a background service read `~/Downloads`, `~/Documents` or `~/Desktop`, so the code lives outside them.

### Avatars

An avatar's spritesheet is one image with a grid of 8 columns and 4 rows, each cell 192 by 208 pixels. Each row is one animation and each cell in it is one frame. The app animates an avatar by showing one cell at a time from the row it wants.

| Row | State | Frames | Shown when |
| --- | --- | --- | --- |
| 0 | `resting` | 6 | Nothing is happening, and greyed out when the server can't be reached |
| 1 | `working` | 6 | The agent is running a turn |
| 2 | `replied` | 6 | A reply the person hasn't opened |
| 3 | `failed` | 8 | The last turn failed |

`skills/make-avatar/render.ts` builds every frame from the avatar's `design.json`. Each row applies the same changes to the one grid: eyes open, blinking, looking down, happy or crossed, a hop, a heart or a sweat drop, and grey colours for `failed`. The agent writes `design.json` into `~/.sidebots/avatars/<avatar-id>/`, runs the script, and looks at the result before replying.

The starter avatars live in the repository's `avatars/` folder and are copied into `~/.sidebots/avatars` on the server's first start.

### Adding a person

The person who runs the server adds each person once, with a name and a Claude Code config folder of their own: `pnpm add-person <name> <claude-config-dir>`. The other commands know the person by that name, so each person on a server has a different one.

The person's agents then sign in to Claude in one of two ways:

- **A Claude login.** The person signs in to Claude Code in their config folder themselves.
- **An API key.** The person who runs the server puts the key in a file and saves it with `pnpm api-key <person> <file-holding-the-key>`. The key comes in a file so that it is never typed into a command the shell remembers. The agents sign in with the key, and nobody signs in to Claude Code.

The store keeps the keys in `~/.sidebots/api-keys.json`, by person, readable only by the server's user account, as it keeps `machine.json`. A person with a key there runs on it from their next turn, and saving another replaces it. `pnpm api-key <person> --remove` takes the key away, and the person runs on the login in their config folder again. Claude Code uses a key ahead of a login, so a key takes over even in a config folder that is signed in. A person with no key runs on the login in their config folder.

A key is in no log line, no response to the phone and no failure notice: if an error from Claude Code quotes the key, the runner takes it out before the notice is saved. Claude Code gets the key in its environment, so an agent's own commands can read the key it runs on, as they can any file of the server's user account.

### Running a turn

For each queued message, the runner calls the SDK's `query` once, in its streaming input mode, with:

- `cwd` set to the agent's home folder
- `resume` set to the agent's `session_id`, when it has one
- `env` carrying `CLAUDE_CONFIG_DIR` for the person who owns the agent, and `ANTHROPIC_API_KEY` when that person has a key
- `settingSources` of `user` and `project`, so the person's skills and connections load along with the agent's `CLAUDE.md`
- `systemPrompt` set to the `claude_code` preset, which is Claude Code's full prompt. Without it the SDK uses a short one that leaves out memory
- `settings` that turn Claude Code's memory on and set its folder to the agent's `memory/`
- `skills: 'all'`
- `permissionMode: 'auto'`
- `model` and `effort` set to the agent's
- `abortController`, which stops the turn if its agent is deleted

Files sent with a message are saved in the agent's `attachments/` folder before the turn, and the prompt ends with their paths. The agent opens them with its ordinary file tools.

The runner sends each message with its Sidebots id as its `uuid` and `priority: 'next'`. The query stays open while the turn runs, and a message the person sends meanwhile goes into it. Claude Code reads it at its next pause between steps. Every frame it sends names the messages it has read so far in `user_message_uuids`, and the runner marks each one read as it first appears. A result names the messages its reply answers. The runner saves the reply, marks those messages done, and closes the query once every message sent to it has its reply and no background work the agent started, such as a long command, is still running. The SDK reports that work in `background_tasks_changed`. When it finishes, Claude Code wakes the agent by itself, and the result of that turn names no message: the runner saves it as a reply like any other. The query waits for background work for 30 minutes at most, then closes, which stops it. A follow-up that arrives as the turn is finishing gets a reply of its own in the same session.

The runner stores the session ID from the last result on the agent. A turn ends with its query, so the server keeps no long-lived state and a restart loses nothing. Each agent runs one turn at a time.

When a message answers an earlier one, the prompt starts by quoting it.

### Updates during long work

For a turn the person is waiting on, the runner gives the agent a `send_update` tool. Its description tells every agent to use it only when work takes a long time, to say in a sentence or two what is done and what is left, and not to repeat it in the final reply. The server enforces the timing: an update in the turn's first minute, or within three minutes of the last, is refused with words telling the agent to carry on. An update is saved as a message from the agent with `interim` set.

### Jobs

The runner gives each agent three tools beside `search_history`: `schedule_job`, `list_jobs` and `cancel_job`. A job is what to do on each run, written by the agent to itself, and a schedule. Times are the server machine's local time, and the tools' answers tell the agent the time now.

A clock in the server looks every 15 seconds for jobs whose time has come and starts their agents' queues. An agent's queue runs the messages it was sent first, then any job that is due, one turn at a time, so a job never runs alongside a reply in the same folder.

A job's run is a new session that is not saved (`persistSession: false`), on the agent's model, in the agent's folder. It never touches the chat's session, so a job that runs every few minutes doesn't fill it. The prompt gives the run the job's instructions, tells it to keep what the next run needs in memory, and tells it to reply with only the word `SILENT` when there is nothing worth telling. Any other reply is saved as a message from the agent, with the job's id, and notifies the phone. The chat's session never saw that message, so the person's next message carries what the jobs sent since the agent's last reply.

After a run, an interval counts from the end of the run, a daily job moves to its next day, and a job set for one time is removed. After the machine has been asleep or off, each job that was due runs once. A run that fails adds a failure notice to the chat, unless the latest message there is already one.

### Replacing a session

A session is replaced when the person asks for a fresh start, or when a turn ends with the session holding more than 120,000 tokens. The size comes from the usage on the agent's last step, which counts everything the model read for it.

A fresh start is a message from Sidebots that waits in the agent's queue like any other, so it runs after the turns ahead of it. The runner first runs one turn asking the agent to save what is worth keeping to its memory, and then clears `session_id`. If that turn fails the session is replaced anyway, since the chat is still there to search. The next turn starts a new session whose first prompt includes the 20 most recent messages from the database.

### Pairing a phone

`pnpm pair <person> --host <address>` makes a pairing code and prints it as a QR code and as a link. `host` is the address the phone reaches the server at, such as the machine's Tailscale name, and is the machine's own address from the relay when left out. The code is 32 random bytes. The store keeps only its hash, with the person it is for and when it expires, ten minutes later.

The QR code holds one link:

```
sidebots://pair?host=<address>&code=<code>
```

The phone sends `POST /pair` to that host with `Authorization: Pairing <code>`, its contract version in `Sidebots-Contract`, and its own name. The server refuses a phone on another version, or one that sends no version, before it looks at the code. Otherwise it checks the code, deletes it, and answers with a device key and a notification key, each 32 random bytes, and the machine's name for the app to show. The phone sends the key on every later request as `Authorization: Bearer <key>`. The store keeps the key's hash, never the key. The api matches each request's key to a paired phone and its person, and answers 401 to a request with no known key.

`pnpm devices` lists the paired phones, and `pnpm remove-device <id>` deletes one, so its next request gets 401. `pnpm status` says whether a server answers on the port and at the machine's address, and how each person's agents sign in. With `--json`, `status`, `devices` and `pair` print JSON for the Mac app. The server and these commands open the database at once, so each waits up to five seconds for the other's lock.

### Looking at past messages

One search in the store finds the messages that contain a word or phrase, across all agents that belong to the same person, newest first. The runner gives it to each agent as a `search_history` tool, built with the SDK's `createSdkMcpServer` and `tool`. The app's search field reaches it through `GET /search`.

### Notifications

Only the Apple Developer account that built the app can notify it, so the server sends notifications through a relay, a Cloudflare Worker in `relay/` that holds that account's push key and passes each notice to Apple's push service. `SIDEBOTS_RELAY` names the relay, and is `https://relay.sidebots.app` unless set. With `SIDEBOTS_RELAY=off` the server sends none, and everything else works.

The server registers with the relay the first time it sends a notification. It makes an Ed25519 key pair, keeps the private key in `~/.sidebots/machine.json`, readable only by the server's user account, and sends the public key to `POST /machines`, which answers with the machine's id. Every request to the relay carries `Authorization: Signature <machine>:<time>:<signature>`, where `machine` is the id, or the public key when it registers, and the signature covers the method, the path, the time and the body's hash. The relay refuses a request whose time is more than five minutes from its own. `POST /notifications` takes the phone's token, its push service, the encrypted notice and its message id, and answers `sent`, `gone` or `failed`. The relay sends a machine at most 1000 notifications a day, and removes a machine it hasn't heard from in 60 days. A removed machine registers again with the key it has, the next time it sends one. The relay keeps each machine's public key and id, and nothing about people, agents or messages.

The relay can't read a notification. The server encrypts each notice, the agent's name, what it said, the count for the app's icon and the agent's id, as JSON with AES-256-GCM under the phone's notification key: the 12-byte nonce, the encrypted JSON and the 16-byte tag, in base64. The relay sends Apple an alert that says "Sidebots" over "New message", with `mutable-content` set, the message id as its collapse id, and the encrypted notice beside it. On the phone, the notification extension in `mobile/targets/notifications`, the small program iOS runs as a notification arrives, reads the key from the Keychain group it shares with the app, opens the notice, and shows the agent's name over what it said, with the count and the agent's thread. When it can't, the notification shows as the relay sent it.

The app gives the server its device token once the person allows notifications, and again on each return to the app. The server sends a notification when an agent's reply is saved and when a turn fails, unless the agent is muted. An update during long work sends none. Each one carries the number of replies and failure notices the person hasn't read across their agents that aren't muted, which the app's icon shows, and the sound `sidebots.wav`, which the app carries in its bundle. When Apple says a token is no longer in use, the server forgets the token, and the phone stays paired.

An agent's unread count is its replies and failure notices newer than its `read_at`, not counting updates during long work. Opening a chat sets `read_at` through `POST /agents/:id/read`, which clears the count on every phone.

### API

| Route | Purpose |
| --- | --- |
| `GET /agents` | The person's agents with their latest message and unread count |
| `POST /agents` | Create an agent |
| `PATCH /agents/:id` | Change an agent's name, avatar, model or effort, or whether it is muted or hidden |
| `DELETE /agents/:id` | Remove an agent and everything it had |
| `GET /agents/:id/about` | The agent's instructions, memories and jobs |
| `DELETE /agents/:id/jobs/:job` | Remove one of the agent's jobs |
| `GET /agents/:id/messages?after=<message-id>` | The newest page of messages, everything after a known message, or with `before=<message-id>` the page before one |
| `POST /agents/:id/messages` | Send a message, as a form with `body`, any `files`, and `replyTo` for the message it answers. Text alone can be JSON |
| `GET /agents/:id/attachments/:name` | A file that was sent with a message |
| `POST /agents/:id/read` | Mark the chat read up to now |
| `POST /agents/:id/fresh-start` | Replace the current session |
| `GET /search?text=<words>` | The messages that contain the words, in any of the person's chats |
| `GET /avatars` | The avatars on the server |
| `GET /avatars/:id/spritesheet` | An avatar's spritesheet |
| `POST /pair` | Pair a phone that brings a pairing code, and give it its key |
| `PUT /push-token` | Say where Apple delivers the phone's notifications |
| `GET /events` | Live stream, as server-sent events. Each event is a message that was added or changed status, with its agent as the home screen shows it; a new agent, the same way with no message; or the id of a deleted agent |

Every route but `POST /pair` takes a paired phone's key and only returns that phone's person's agents and messages.

Every response, a refusal included, carries the server's `CONTRACT_VERSION` from `contract.ts` in the `Sidebots-Contract` header. The number goes up when a change means an older app or server can't work with a newer one. The app compares it with its own and uses nothing a server on another version says. A server that sends no header counts as older. The app sends its own version in the same header, and the server refuses to pair an app on another version.

### Phone app

The app lives in `mobile/` and uses Expo Router, where each file under `src/app` is a screen. It has five screens and three sheets: welcome, pairing, home, the chat and the camera, and the sheets for a new agent, an agent's page, and a note opened from that page. Photos come from `expo-image-picker`, the camera and the pairing screen's scanner from `expo-camera`, files from `expo-document-picker`, and notifications from `expo-notifications`. The + menu and the chat's menu are the system's own menus, drawn by a small native module in `mobile/modules/message-menu` copied from Assist: a clear iOS menu button laid over what the person taps. The swipes on a row of the home screen and on a message come from `react-native-gesture-handler`. The keyboard moves the message field and the home screen's search field through `react-native-keyboard-controller`, which follows the keyboard on the UI thread, frame by frame. The playful lines shown while an agent works are a list inside the app. An avatar view takes a spritesheet and a row and draws the frames in turn, and the app caches spritesheets on the phone. The app keeps a local copy of agents, messages, what each opened agent page showed, and the changes to agents the server doesn't have yet in Expo's SQLite key-value store. Those changes are laid over whatever the server sends until the server has them, so a reply arriving mid-change can't undo one. While open, it listens to `GET /events`. On launch and on returning to the foreground, it reconnects and fetches the newest page of each chat it has opened. The app keeps the server's address in the same store and its two keys in the Keychain, through `expo-secure-store`, in a group it shares with its notification extension. It sends the device key with every call, the event stream, and each avatar and attachment it loads. Until the phone has paired, welcome and pairing are its only screens. A 401 from the server clears the pairing and the saved chats. The event stream reads the server's contract version each time it connects, and the home screen shows which side to update while they differ.

## Testing

The server is tested through its HTTP routes, with the runner swapped for a fake that returns set replies. That covers ordering, queuing, failure messages and the per-person filter without spending anyone's usage. One manual check per slice runs a real turn through Claude Code. The app is checked in the iOS Simulator and then on a phone over Tailscale.

## Out of scope

- Live voice
- Chats shared between two people
- One build of the app shared by several households
- Agents that talk to other people's agents
- A Sidebots sign-in of its own, such as Google sign-in
- An Android build, and any client other than the phone app
- Driving websites that need a typed password
- Moving the server off the MacBook

## Work breakdown

Each slice ends with something that works on its own.

1. **One agent, no app.** Server, database, one agent folder, and the runner. Sending a message with `curl` returns a reply. This proves the subscription login, skills, connections and auto mode work through the SDK.
2. **Chat on the phone.** The server setup screen, the chat screen, the event stream, and Tailscale. A message typed on the iPhone gets a reply from the agent on the MacBook.
3. **Many agents.** The home screen, creating an agent from the plus button, avatars and the avatar picker, and identifying the person from their Tailscale login.
4. **Notifications.** Device registration and a notification when a reply lands.
5. **Attachments.** Sending a photo or file into the agent's folder.
6. **Memory and fresh start.** Memory files, replacing a session by hand and by size, and `search_history`.
7. **Making avatars.** An agent makes a new avatar with the `make-avatar` skill.
8. **Agents you can manage.** Jobs, the agent page, the model and effort, mute, hide and delete, replies to a message, and older messages.
9. **Second person.** A second config folder and Claude login on the server, a second Tailscale user, and the TestFlight build on both phones.
