# Sidebots

15 November 2026

## Summary

Sidebots is a messaging app for agents that a household runs for itself on its own machine. Each chat in the app is an agent. You send it a message, it does the work, and a finished reply arrives like a text from a person. The agent runs on a machine we own, using Claude Code or Codex, and each person pays for their own agents' usage, on their Claude or ChatGPT subscription or on an API key.

Hosted products such as Grok Bot do this for $30 to $200 a month per person and keep the data on their servers. Sidebots reuses the Claude and ChatGPT subscriptions we already pay for, plus the skills and connections Claude Code and Codex already have.

## Decisions

- **Each household runs its own Sidebots.** The code is open source. Every agent on a server runs as the same user account on that machine and can reach that account's files, so a server is shared only by people who trust each other with that machine. Anyone else runs their own server and builds their own copy of the phone app.
- **Nothing personal is in the code.** The people, their paired devices, their providers' config folders and their API keys live in `~/.sidebots`. The phone app pairs with its server on first launch. The Apple team and app identifier come from `mobile/.env.local`, which is not committed.
- **A server and two clients.** A server written in TypeScript on Node, a phone app written in TypeScript with React Native and Expo, and a desktop app written in TypeScript with Electron, which `docs/specs/2026-11-21-desktop-app.md` describes. React Native draws real native views, and the same code can build an Android app later. The apps import the server's wire types from `server/src/contract.ts`, so they can't drift apart, and share their client logic in `client/`. There is no web client. The Mac app in `mac/` holds the server and carries the desktop app.
- **The server runs on the MacBook,** as a service macOS starts at login and restarts if it stops. It can move to any machine that runs its providers by copying `~/.sidebots` and, for each person who uses a login, signing in to their providers there.
- **A provider does the agent work.** A provider is the program an agent runs on, and each agent runs on one. Sidebots has two, Claude Code and Codex, and a person picks one as they make an agent, from those they have set up, and can move the agent to another later. Sidebots carries neither program. The server finds the ones installed on the machine, the way a terminal there does, and runs each when it is no older than its driver works with. The server drives Claude Code through the Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`). The SDK starts the installed Claude Code, which runs each turn on its owner's Claude login or API key. It drives Codex through `codex app-server`, the program Codex's own apps drive it with. Each provider has a driver in the server, and the rest of the server and the app work the same whichever provider an agent runs on.
- **Each person pays for their own agents, with a login or an API key.** Each person has a config folder of their own for each provider their agents run on. For Claude Code, the server sets `CLAUDE_CONFIG_DIR` to that folder for every run that person triggers. It leaves Claude Code's own folder, `~/.claude`, unnamed: Claude Code keeps the login of a folder it is pointed at apart from the one it finds there by itself, so naming it would hide a login the person already has. Claude Code keeps the person's sessions there and loads their rules, skills and connections from it. With a Claude login, the person signs in to Claude Code in that folder themselves, through Anthropic's own sign-in, and their agents use their subscription. Sidebots never reads, stores or passes on a login. With an Anthropic API key, the person who runs the server saves the key in `~/.sidebots`, the server hands it to Claude Code for every run that person triggers, and Anthropic bills the key's account. A person with a key needs no sign-in. Codex is the same with `CODEX_HOME`, a ChatGPT login and an OpenAI API key. Its driver hands a key to each Codex process to keep in its memory, so a login in the same folder is left as it is.
- **Anthropic's terms decide which of the two a person may use.** A subscription is for the subscriber's own use, so a household that runs Sidebots for itself can use its own logins, each person signing in themselves. For a product built on the Agent SDK, Anthropic asks for API keys and doesn't allow Claude logins to be offered to the product's users without its approval. So anyone who sets Sidebots up for other people reads the terms first and, when in doubt, gives each of them a key. OpenAI's terms decide the same for a ChatGPT login.
- **A chat and a session are different things.** A chat is the endless list of messages a person sees, stored by Sidebots. A session is what the model reads, stored by the agent's provider. An agent has one chat for its whole life and one current session that gets replaced when it grows large. A session that never ends gets slower, less accurate, and costs more per message, because the model rereads all of it on every turn.
- **Only replies, the agent's own updates, its asks and what it says to another agent are messages.** Tool calls and the agent's working steps stay in the provider's own record of the session. They are never stored in Sidebots or shown in the app. During long work the agent may send a short update of its own choosing. A reply or an update can carry files the agent chose to send. An action the provider won't decide by itself shows as an ask, for the person to allow or not.
- **An agent belongs to one person.** Two people never share a chat, so it is always clear whose subscription or API key a reply uses. Shared information lives in Notion.
- **Each agent has a home folder.** The agent runs there. The folder holds its instructions, its memory and the files sent with the chat's messages, the person's and its own.
- **Memory is Claude Code's own.** Claude Code already keeps notes between sessions: a `MEMORY.md` list it reads at the start of each session, and one file per thing it has learned. Sidebots points that feature at the agent's `memory/` folder, so what an agent learns outlives every session and moves with `~/.sidebots`. It is on for Sidebots' agents even when their owner has turned it off for their own Claude Code. Codex keeps what it remembers in its config folder, for everything that runs there, so a Codex agent keeps the same files itself: its driver tells it how in Codex's prompt, and turns Codex's own memory off for the agent's sessions.
- **Each agent has its own model, effort and speed.** A new agent on Claude Code starts on Opus at medium effort. The person picks from Fable, Opus, Sonnet and Haiku, by the names Claude Code gives them, so each always means the newest model of its kind, and from every effort Claude Code has: low, medium, high, extra high and max. One on Codex starts on Sol, and picks from Astra, Sol, Terra and Luna, and from Codex's efforts, which are those five and ultra. The apps show each model by its full name with its version, as "Claude Opus 5.5" and "GPT-6.2 Sol", from `PROVIDERS`, which names the newest of each kind as T3 Code's model list does. A model that hasn't the agent's effort runs at the highest it has. Codex names a model for its version too, as `gpt-6.2-sol`, so its driver asks Codex which it offers and runs the newest of the kind. A model with a fast mode can answer in it, which is sooner and uses more of the plan or credit: Fable and Opus on Claude Code, through Claude Code's `fastMode` setting, and every Codex model, at the mildest of the faster tiers Codex lists for it. Each turn says which speed it wants, so the person's own Claude Code or Codex settings don't decide it. Sidebots has no other model settings.

- **What an agent answers with can change mid-chat, its provider too.** The person picks a provider they have set up, one of its models, an effort and a speed, and the choice takes effect from the agent's next turn. The runner records what each turn runs on as the turn starts, in `ran_on`, and compares the next turn with it, so several picks are one change, picking the old again is none, and a pick made while a turn runs counts from the turn after it. Before the turn that first runs on the new choice, the chat gets a notice from Sidebots that carries the change in `switched`: what the agent answered with before, and what it answers with now. On the same provider the session carries on. A session doesn't cross providers, so an agent that moves with a session going is handed over as for a fresh start: it saves what is worth keeping to its memory in the session it had, on the provider it had, and its next turn starts a new session on the new provider that is shown the latest of the chat. The notice is `running` while it hands over. The agent's memory folder is the same on both, and its instructions move to the file the new provider reads.
- **Each agent keeps its own instructions and memory.** Sidebots gives every agent the same few starting lines and no shared rules after that.
- **Jobs run by Sidebots' own clock.** Claude Code's own scheduled tasks only fire while a session is open, and its cloud ones can't reach this machine's files. Sidebots runs one call per turn, so the server keeps the schedule and starts each run itself.
- **Sidebots counts usage as each turn ends.** It runs every turn itself, so it records what each one cost and the tokens it used, by its provider's own count, and what the turn was for: a reply, a job's run or the memory save before a fresh start. Nothing could be read back from a provider's history afterwards, since a job's run saves no session. What is left of a plan comes from the person's own Claude Code or Codex: what it says while a turn runs, and what it answers when Usage is opened. Sidebots never asks Anthropic or OpenAI itself with a person's login.
- **Agents run under their provider's own safety check.** On Claude Code that is auto mode: Claude Code checks each action with its own safety classifier and runs the ones it judges safe. An action the classifier can't decide on goes to the person as an ask in the chat, and the agent waits for their answer. On Codex it is the sandbox and the reviewer. The sandbox lets an agent write in its own folder and read the rest of the machine. Whatever needs more, such as the network or a file elsewhere, goes to Codex's reviewer, a model that allows what is safe and what the person asked for, and refuses the rest. Sidebots adds one restriction of its own: on Codex, whose reviewer judges only what an agent runs on the machine, a tool of Sidebots' that acts as the person outside it, as sending a mail does, asks the person first. A tool that an app's own server gives is the provider's to judge, as it judges a tool of any server in the person's setup.
- **Agents load their owner's setup for their provider.** Whatever global rules, skills and connections that person has in their config folder for Claude Code or Codex apply to their Sidebots agents on it too. Connectors the person added on claude.ai come only with a Claude login.
- **A person connects an app once, in Sidebots, for all their agents.** Gmail, Google Calendar and Notion are connections made in Sidebots, so an agent has them on either provider and on an API key as on a login. The person signs in on the app's own page, on their phone or in the computer's browser. What the app gives for acting as them stays on their machine, and neither the relay, the phone nor the desktop app keeps it.
- **Sidebots data lives in `~/.sidebots`,** separate from the code. Messages live in one SQLite file, the same approach T3 Code takes with `statev2.sqlite`.
- **The phone reaches the server through a Cloudflare Tunnel.** The server listens on the local machine only. `cloudflared` holds a connection open from the machine to Cloudflare, which gives the machine an address of its own under `sidebots.app` and brings the phone's requests along it, from anywhere and with nothing to change on the router. A rule on the zone refuses any request to that address without an `Authorization` header, and the server refuses any without a paired device's key. A server run with the relay off can be reached over Tailscale instead.
- **Pairing tells the server who is asking.** The server makes a one-time code for a person, that person's phone scans it and gets a key of its own, and the server refuses every request without a known key. The desktop app pairs the same way, with a code it has the server make. Sidebots has no accounts, passwords or sign-in screen.
- **The server is the source of truth.** Each app keeps a local copy of messages so chats open instantly and work offline, and it refills that copy from the server.
- **Every agent has an avatar.** An avatar is an animated pixel character that acts out what its agent is doing.
- **People make their own avatars by asking an agent.** Claude can't paint images, but it can write pixel art as a grid of letters. Sidebots' `make-avatar` skill has the agent draw the avatar once as a 16 by 16 grid, and a script turns that grid into every animation frame. Every avatar moves the same way and the whole thing runs on Claude.
- **The app installs through TestFlight,** built with the Apple Developer account of the person who runs the server. The server sends notifications through a relay that holds that account's push key.

## Behavior

**First launch.** The app opens on a welcome screen: the app's icon, one line on what Sidebots is, and the two steps to pair, getting Sidebots for the computer from sidebots.app, and choosing Pair a phone in its Settings and scanning the code. Its one button, "Scan the code", opens the camera, and only then does the phone ask for the camera. The camera is laid out as the chat's camera: the preview on black, with one line under it asking for the code the server made for the person, and a back button above it. If the person refused the camera, a button in its place opens Settings. Scanning the code pairs the phone, the line names the machine it paired with, and the app opens on the agents. A link button above the preview asks for the same code as its link, in the system's own prompt, and a pairing link opened anywhere on the phone pairs it too. A code works once, for ten minutes unless it was made to work for longer. A phone the server doesn't know goes back to the welcome screen, with its saved chats cleared and a line saying the computer removed it. The line stays, through relaunches, until the phone pairs again.

**Home.** The app opens on the person's agents, each with its avatar, its name and its latest message. In a window as wide as an iPad held upright, the agents stay in a column at the left, and the chat a tap opens shows beside them, in place of the one before it, with its row marked. There is no title bar and no heading. Glass buttons float at the top: one for the side menu on the left and, on the right, one for search and one for a new agent. Search puts a glass field in their place, with the keyboard up and a button to close it. Typing in it lists the agents whose name matches, then the messages that contain the words, from every chat. A tap on either opens that chat. An agent with replies the person hasn't read shows how many, in a round count at the end of its row. A person with no agents yet sees "No agents yet" with a line pointing at the + button, and no search button. A swipe left on an agent shows Mute, Hide and Delete. A muted agent sends no notifications, stays out of the count on the app's icon, and shows a small crossed bell by its name. A hidden agent leaves the list and waits under a "Hidden" line at its end, which a tap opens. It comes back by itself when it next has something to say, unless it is muted. Search finds hidden agents too. An agent the person adds, changes or deletes on another of their devices comes, changes or goes here at once.

**Side menu.** The menu button, or a swipe right anywhere on the home screen or the agents' column, slides the screens aside to uncover a menu. At its top is the computer the phone paired with, by name, with a dot and a line that say whether the phone reaches it: "Connected", "Out of reach", or which side to update when the versions don't match. Under it are Usage and Connections. At its foot are the privacy policy, Disconnect and the app's version. Disconnect asks first. The computer then forgets the phone, with its keys and where its notifications go, and the phone goes back to the welcome screen with its saved chats cleared. The agents and their chats stay on the computer. When the computer can't be told, as when it is off or gone for good, the app says why and offers to disconnect anyway, and the computer lists the phone until the person removes it there.

**Usage.** Usage, in the side menu, opens a sheet that says where the person's plan goes. At its top is the plan: each of its limits, such as the weekly one, with how much of it is left, in words and as a bar, and when it resets. The computer asks Claude Code where the limits stand as the sheet opens, so the sheet says when Claude Code said, and that the limits count what the person uses outside Sidebots too. When Claude Code has said nothing, as when it is signed out, the sheet says it hasn't said. For a person on an API key the sheet says there is no plan to run out and that the key is billed instead. Below are the last seven days, today among them, by cost or by tokens as the person picks. First comes what the seven days used in all, over a bar for each day, the tallest the day that used most. Pressing a bar shows what that day used in place of the total, and pressing it again brings the total back. Then comes every agent that ran a turn in those days, the one that used most first: its avatar and name, what its turns used, its share of what all the agents used as a bar, and its use split into replies, jobs and fresh starts. A turn's tokens are everything its model read and wrote, what it read again from its cache among them. A cost is an estimate in US dollars at Anthropic's API prices, by Claude Code's own count. An API key is billed for it. On a plan the cost is no bill, and measures where the plan's limits go. Anthropic charges a plan for use past its limits only where the person has turned usage credits on. The sheet says so.

**Connections.** Connections, in the side menu, opens a sheet that lists the apps the person's agents can use as them, each with its logo: Gmail, Google Calendar and Notion. One that isn't connected says what connecting it lets the agents do, beside Connect. Connect opens the app's own sign-in in the sheet iOS has for signing in, and once the person has signed in and allowed what the app asks for, the row says which account it is connected as, beside Remove. Remove asks first, and then none of the person's agents can use the app. A turn that is running may go on using Notion until it ends. A person can also tell an agent to connect an app, and an agent that needs one that isn't connected asks for it: a card in the chat names the app, with its logo, and what connecting it allows, with Connect and Not now. The agent waits, as it does for any ask, and goes on with what it was doing once the person has signed in. An agent on Codex has Notion's tools from its next turn.

**Chat.** Opening an agent shows the full message history. A new agent's chat, until its first message, says "<name> is new. Tell it what it's for." Nothing at the top of the chat is a bar: a glass back button and the agent's avatar with its name in a pill float over the messages, which scroll behind them. The message field sits at the bottom on a strip of the page colour, and opens and rises with the keyboard as Assist's does. The person sends text, photos or files. The + in the message field opens a menu of Photos, Camera and Files, as Assist's does. Before Send, the field has a square button with the logo of whoever makes the agent's model, Claude's for Claude Code and OpenAI's for Codex. A tap on it brings up a drawer with the provider's models and its efforts, a row to each, with a check by the one of each in effect, and under them Standard and Fast when the model has a fast mode. A person who has set up more than one provider picks between them above the models, and a model of another provider moves the agent there. Choosing another takes effect from the agent's next turn, and the drawer stays up until it is swiped away. A change shows in the chat before the first reply that comes from it, as a line across the chat with what the agent answered with before, faded, a row of three dots, and what it answers with now: only the parts that changed, or all of both after each provider's logo when the agent moved. The dots light in turn while the agent hands over to the new provider. Camera opens full screen with a quick fade and takes photos one after another, each joining a row under the preview, and Add puts them all in the message. What they pick sits in a row of tiles above the text until it is sent, up to ten and 95 MB to a message. A sent message shows straight away, faded until the server has it. Under the person's newest message a receipt says "Delivered" while it waits for the agent, and "Read" with the time once the agent has taken it in. In the chat, one photo shows in its own shape and several show as square tiles. A tap opens them full screen, to swipe between, pinch and share. A file shows as a card with its kind and opens in the share sheet. The agent sends photos and files too, with a reply or an update, and they show above its text as the person's do. A page the agent wrote as HTML, such as a chart or a table, shows as the page itself, as T3 Code shows one: drawn in the chat under its name, in the chat's colours, light or dark, and as tall as what it holds up to most of a screen. A longer page fades out there, over "Show all". That and the button beside its name open it full screen, to scroll, zoom and share. The page is closed off from the app, and a web link tapped in it opens in the Safari sheet. While the agent works, the avatar at the top plays its working animation, and the end of the chat shows three dots that light in turn beside a short playful line that changes every few seconds. The line says nothing about what the agent is doing. The reply arrives as one message. The agent's replies show as rich text, as T3 Code shows them: GitHub's markdown, with headings, lists, task lists, quotes, tables, highlighted code and links. The text is selectable. A web link opens in a Safari sheet over the app, and any other link opens the app that handles it. The chat list and notifications show a reply as plain words. A swipe left on any message replies to it, as in Telegram, since a swipe right anywhere in the chat goes back: the message is quoted above the field until it is sent or let go, the sent message shows the quote at the top of its bubble, and the agent is told which message it answers. Scrolling up to the oldest message on the phone fetches the ones before it. What the person has typed stays in the field when they leave the chat and come back. A tap on the agent's avatar or name opens its page.

**Agent page.** The page opens on the agent's avatar, large, with its name and the model and effort it answers with under it. Edit, at the top left, turns the name into a field and brings up the avatars to choose from, and the large avatar changes as one is picked; Save keeps both and Cancel leaves them. Below the avatar are two tabs. Settings holds what the agent used in the last seven days, switches for Mute and Hide, and Delete. What it used is a row for each kind of turn it ran, its replies, its jobs and its fresh starts, with how many turns and what they cost. Jobs & memory holds what the agent works from: its jobs, each with when it runs, when it next runs and what it does, and a button to remove it; the instructions it follows; and what it remembers. Instructions and memories open to read in full, as rich text, as the agent's replies show. The agent writes all three itself, as the person tells it things in the chat.

**Jobs.** The person asks an agent, in its chat, to remind them of something or to keep an eye on something, and the agent saves a job: once at a time, at a time of day on every day or on chosen weekdays, or every so many minutes. Sidebots runs the job when its time comes. If the run finds something worth telling, it arrives as a message from the agent with a notification. Otherwise nothing shows. An agent can list and remove its own jobs when asked, and the person can remove one from the agent's page.

**Deleting an agent.** Delete asks first, since nothing comes back. It removes the agent's chat, its jobs, the count of what it used, its home folder with its instructions, memory and attachments, and the sessions each of the person's providers kept for it. A turn it is running is stopped, and its chat closes if it is open.

**Away from the app.** The agent keeps working after the phone is locked or the app is closed. When the reply is ready, the agent asks before an action, or the turn fails, the phone shows a notification with the agent's name over what it said, with Sidebots' own soft two-note sound. Tapping it opens that chat. A notification is for what the person hasn't read: one comes two seconds after its message, and only when the message is still unread, so a reply they read as it comes, in the chat they are looking at on the computer, reaches no phone. Once they read a chat on another device, its notifications leave the phone. The app's icon shows how many replies are unread across all agents. The app asks to send notifications the first time the person sends a message. While the app is open no notification shows or sounds, since the chat list already has the counts.

**On the Lock Screen and in the Dynamic Island.** While an agent works, its avatar shows on the Lock Screen and in the Dynamic Island as a Live Activity: the avatar in its working pose, the agent's name, one of the playful lines, and a clock that counts up from when it appeared. It appears as the agent starts work with the app open, and stays when the person leaves the app, locks the phone or closes the app. When the work ends, the activity leaves the Dynamic Island, and on the Lock Screen the avatar changes to its replied pose over "Replied", or to its failed pose over "Couldn't finish". It stays there for 15 minutes, or until the person next opens the app. A tap on the activity opens that agent's chat. Each working agent has an activity of its own, and a muted agent has none. Under the first activity, iOS asks once whether Sidebots may show them. The avatar holds one pose in each state, since iOS draws a Live Activity again only when its state changes. The activity never shows what the agent said. That comes in the notification.

**Sending while the agent is busy.** The message is saved and shown straight away. If the agent is working on the person's earlier message, the new one goes into that turn: the agent reads it at its next pause between steps and answers both in one reply, which steers the work while it is under way. A message sent while the agent runs a job, or replaces its session, waits for its own turn.

**Stopping an agent.** While an agent works and the message field is empty, the Send button is a Stop button. A tap stops the turn the agent is running, usually within a second: a command it was running ends, the working line goes, and a "Stopped" line marks the place in the chat. The agent keeps its session and knows it was stopped, so the next message carries on from there. The person's messages stay in the chat. One the agent had read is in its session. One it hadn't read yet, sent into the turn or waiting behind it, shows "Send again", as after a failed turn. A message sent after the stop gets its own turn. Stopping a fresh start calls it off, and the agent keeps its session. Stop is there whenever the chat shows the agent working. So it isn't there while the server can't be reached, or during a job's run, which shows nothing until it has something to say.

**Long work.** When work on a message runs long, the agent may send a short update of where it has got to. It can send the first only after a minute, and then no more than one every three minutes. An update shows in the chat like a reply but arrives quietly: it sends no notification, doesn't count as unread, and doesn't bring a hidden agent back. The final reply does all three. Jobs send no updates. If the agent starts work that runs on in the background, such as a long command, its session stays open for up to half an hour, and when the work finishes the agent picks it up again and sends its result as a new reply.

**New agent.** The person taps the plus button on the home screen, gives the agent a name and picks an avatar from the ones on the server. A person who has set up both providers on their computer also picks the one it runs on, which starts as the first they set up. Its chat opens straight away. The server creates its home folder with a standard set of instructions, and the agent adds to them as the person tells it what it is for.

**Motion.** Nothing on screen snaps into place. A message that comes into an open chat rises into place as it fades in, and the person's own settles from its faded copy where it already sits. The chat the person opens shows as it is. The working line fades in when work starts and out as the reply comes, and its words crossfade as they change. Text that changes, such as a receipt, an agent's latest message on the home screen or a hint, crossfades from the old words to the new. On the home screen, rows slide to their new places as an agent moves up, and fade in and out as they come and go. Unread counts grow in and shrink away. A choice such as the agent page's tab slides its mark to the new one. Everything follows the phone's Reduce Motion setting.

**Avatars.** An avatar shows the agent's state wherever the agent appears: resting, working, a reply waiting, or a failed turn. When the server can't be reached, every avatar shows its resting pose, greyed out.

**Making an avatar.** The person asks any agent for a new avatar, describing it or sending a photo. The agent makes it and replies when it's ready, with a picture of it, and the avatar appears in the picker for new agents. Any agent's avatar can be changed from its page.

**Fresh start.** A command in the chat's menu, behind the glass button at the top right, replaces the current session. The messages on screen stay as they are, and a "Fresh start" line marks the place in the chat. The agent first writes what is worth keeping into its memory. A session that grows large gets a fresh start by itself.

**Actions that change things.** The agent acts on its own wherever its provider's safety check lets it. When the check refuses an action, the agent says so in its reply and carries on with the rest of the work. When the check leaves an action to the person, the agent asks: a message from it arrives with a notification. It reads as plain words: what sort of thing the agent wants to do, such as "Run a command", this one thing in a line, the facts that matter, such as the folder a file is in or who an email goes to, and the provider's reason for asking when it gives one. For a command the line is the agent's own account of what the command does, or the start of the command when the agent gave none. The thing itself, the command, the page's address, or the file with what would be written to it, opens on a tap under them. At the foot of the message are two buttons, Allow and Don't allow. The agent stays at work while it waits, and the dots and the playful line leave the end of the chat until the ask is answered, so the ask is the last thing in it. Allow lets it go on. Don't allow has it leave that one thing undone, finish the rest, and say in its reply what it left out. The buttons then give way to how the ask ended: "Allowed", "Not allowed" or "Not answered". An ask waits half an hour. A message the person sends in the meantime answers it instead: the ask closes as not answered, the action is left undone, and the agent reads the message. An agent's job asks the same way, and a message sent while it waits is kept for its own turn, as any message sent during a job is.

**Agents asking agents.** An agent can ask another of the person's agents something, or hand it a piece of work, as when one agent keeps track of everything and the others each know one thing. In the asking agent's chat, what the two say to each other is one line: the two avatars with a dotted line between them, "Mochi asked Cog", and where the newest thing asked stands: "Waiting", "Needs your OK", "Answered" or "No answer". As something is asked, a dot crosses from the asker's avatar to the other's, which nods. What the two ask and answer after that stays in the same line, until the person sends a message or the agent gives them its reply, and what is asked next begins another. A tap on the line opens the exchange as a sheet: a chat of the two agents' own, with both avatars at its top and no message field. The agent that asked first is at the right, in its chat's colour, and the other at the left, each with its avatar beside what it said. While the newest thing asked has no answer, a line at the sheet's foot says where it stands, as "Waiting on Cog". The other agent's chat has a line for the exchange too. While the agent waits, the dots of that line light in turn from the asker to the other, and its row on the home screen says "Waiting on Cog". Whatever it says to the person meanwhile arrives quietly, as an update does, and its reply once it has heard back is the one that notifies. Nobody is notified of what agents say to each other. When the agent that was asked needs the person's answer to an ask of its own, the ask is in both chats, saying whose it is, "Cog asks", and answering it in either settles it. The dots rest, and the line reads "Needs your OK". Stop, in the chat of the agent that waits, stops the other agent's work for it.

**When something fails.** If a turn fails, the chat shows a short message from Sidebots saying why. The common causes are in plain words with what to do on the computer: the provider is signed out there, its usage limit is reached, with when it resets, or its maker refused the API key. Any other failure gives the provider's own reason. The notice never shows the key itself. The person's message is kept, and "Send again" under it sends it as it was, with its photos, its files and the message it answers.

**When the versions don't match.** The app and the server each know which version of their contract they speak. If the server is older, the home screen says "Update Sidebots on your computer" in place of the agents. If the app is older, it says "Update Sidebots from the App Store". Pairing with a server on another version fails with the same words, and leaves the code unused, so it still pairs once one side is updated. The app keeps asking, and the agents come back once the two match.

**When the server can't be reached.** The app shows the saved chats, with every avatar greyed out. Messages typed in the meantime wait on the phone and send when the connection returns. A change to an agent, such as its model, a mute or a hide, shows at once whether or not the server can be reached. It waits on the phone and goes when the connection returns, and only a change the server refuses is undone.

## Design

### Data folder

```
~/.sidebots/

  api-keys.json        each person's API key for each provider they use one with
  connections.json     each person's connections: the account each is signed in as, and the token its app gave
  machine.json         the key that proves this server to the relay, its id and address, and its tunnel's token
  agents/
    <agent-id>/
```

### Database

```sql
create table people (
  id          text primary key,
  name        text not null unique  -- what the server's commands call the person
);

create table accounts (
  person_id   text not null references people(id),
  provider    text not null,     -- the provider's id, such as claude
  config_dir  text not null,     -- the person's config folder for that provider
  primary key (person_id, provider)
);

create table agents (
  id          text primary key,
  person_id   text not null references people(id),
  name        text not null,
  avatar_id   text not null,     -- folder name under ~/.sidebots/avatars
  provider    text not null default 'claude',  -- the provider it runs on
  model       text not null default 'opus',  -- the provider's name for the model it runs on
  effort      text not null default 'medium',  -- the provider's name for how hard it thinks
  fast        integer not null default 0,    -- 1 answers in the provider's fast mode, on a model that has one
  ran_on      text,              -- what its last turn ran on, as JSON, which its session is on; null before its first turn
  muted       integer not null default 0,    -- 1 sends no notifications
  hidden      integer not null default 0,    -- 1 keeps it off the home screen
  color       text,              -- #RRGGBB, the colour of the person's messages in its chat; null takes its avatar's
  session_id  text,              -- the provider's current session, null before the first turn
  read_at     integer not null default 0,  -- the person has read the chat up to here
  chat_changes integer not null default 0,  -- how many times a message in its chat was added, changed or removed
  created_at  integer not null
);

create table messages (
  id          text primary key,
  agent_id    text not null references agents(id),
  sender      text not null check (sender in ('person', 'agent', 'sidebots')),
  body        text not null,
  attachments text not null default '[]',  -- JSON list of paths inside the agent's home folder
  status      text not null check (status in ('queued', 'running', 'done', 'failed')),
  seen_at     integer,           -- when the agent read a message from the person
  reply_to    text,              -- the message this one answers
  job_id      text,              -- the job whose run sent it
  interim     integer not null default 0,  -- 1 for an update the agent sent while still working
  ask         text check (ask in ('waiting', 'allowed', 'refused', 'unanswered')),  -- where an ask stands, null for any other message
  question    text,              -- what an ask asks, as JSON, null for any other message
  peer_id     text references agents(id),  -- the other agent, for a message between two agents or an ask raised while working for one
  switched    text,              -- what the agent answered with before and answers with now, as JSON, for a notice of that change
  created_at  integer not null
);

create table jobs (
  id          text primary key,
  agent_id    text not null references agents(id),
  what        text not null,     -- the agent's instructions to itself for a run
  schedule    text not null,     -- JSON: {type: "every", minutes} or {type: "daily", time, weekdays?} or {type: "once", at}
  next_at     integer not null,  -- when it next runs
  created_at  integer not null
);

create table devices (
  id          text primary key,
  person_id   text not null references people(id),
  name        text not null,     -- "Alex's phone", as the device gave it
  kind        text not null default 'phone',  -- 'phone', or 'desktop' for the desktop app
  key_hash    text not null unique,  -- the hash of the key the device sends with every request
  notification_key text not null,    -- encrypts this phone's notifications, in base64
  push_token  text,              -- the phone's Apple device token, once it allows notifications
  environment text check (environment in ('sandbox', 'production')),
  paired_at   integer not null
);

create table pairings (
  code_hash  text primary key,   -- the hash of a pairing code that hasn't been used
  person_id  text not null references people(id),
  expires_at integer not null
);

create table usage (
  agent_id     text not null references agents(id),
  kind         text not null check (kind in ('reply', 'job', 'memory')),  -- what the turn was for
  cost         real not null,     -- what the turn cost, in US dollars at the provider's prices
  session_id   text not null,     -- the provider's session the turn ran in
  session_cost real not null,     -- what that session had cost in all when the turn ended
  at           integer not null,
  tokens       integer not null default 0,  -- the tokens the turn used: all its model read and wrote
  session_tokens integer          -- the tokens that session had used in all when the turn ended, when the turn was recorded with them
);

create table limits (
  person_id  text not null references people(id),
  provider   text not null,
  name       text not null,      -- what the provider calls the limit, such as "Weekly limit"
  used       real,               -- the part of it that is used, where 1 is all of it, when the provider says
  resets_at  integer,
  at         integer not null,   -- when the provider said so
  primary key (person_id, provider, name)
);

create table activities (
  device_id   text not null references devices(id) on delete cascade,
  agent_id    text not null references agents(id) on delete cascade,
  token       text not null,     -- Apple's token for the Live Activity this phone shows for the agent
  environment text not null check (environment in ('sandbox', 'production')),
  app         text,              -- the bundle identifier of the app the token is for, when it isn't the published app's
  primary key (device_id, agent_id)
);
```

`sender = 'sidebots'` marks messages the server writes itself: failure notices, fresh starts and the line that marks a stopped turn. For a message from a person, `status` is `queued` until the agent reads it, `running` once it has, with the time in `seen_at`, then `done` when it has answered or the person stopped it. It is `failed` when its turn failed, or was stopped before the agent read it. A fresh start goes through the same states while the session is replaced. A failure notice is `failed`. An ask is a message from the agent whose `ask` is `waiting` until the person answers it or the agent stops waiting.

### Server modules

- **store** owns the database and the agent folders. Nothing else touches SQLite or `~/.sidebots`.
- **runner** runs each agent's turns one at a time, on the driver for the agent's provider, gives every provider the same tools for the agent, and has the store record what each turn cost.
- **connections** knows the apps a person's agents can use as them: how the person signs in to each, and the tools it gives the agents, or the server its maker gives them from. No other module signs in to those apps, and none but a provider, which uses a maker's server, asks them anything.
- **claude** is Claude Code's driver. It is the only module that imports the Agent SDK.
- **codex** is Codex's driver. It is the only module that starts Codex.
- **programs** finds the providers' programs on the machine, with their versions, and runs their installers and sign-ins. It is the only module that looks for them.
- **api** owns the HTTP routes and the live event stream, and works out which paired device is asking and whose it is.
- **push** decides when to notify the person's phones, and what each notification says. It tells phones when what they were notified of has been read, and ends the Live Activities phones show for an agent when the agent's work ends.
- **relay** is the only module that talks to the relay. It registers the machine, which brings its address and tunnel, and sends notifications and the ends of Live Activities through the relay.
- **tunnel** keeps `cloudflared` running with the machine's tunnel token, and starts it again when it stops.

### Keeping the server running

The Mac app in `mac/` keeps the server running: it starts the server as a child process, starts it again when it stops, and opens at login. It learns the server's state from the server's own commands, as a person at a terminal does, and between them asks the server's `GET /status` whether it still answers. `docs/specs/2026-11-16-published-app.md` describes it.

Without the Mac app, a launchd agent in `~/Library/LaunchAgents` runs `node src/main.ts` in the `server` folder, with `RunAtLoad` and `KeepAlive` set, and its output goes to `~/.sidebots/server.log`. macOS doesn't let a background service read `~/Downloads`, `~/Documents` or `~/Desktop`, so the code lives outside them.

### Avatars

An avatar's spritesheet is one image with a grid of 8 columns and 4 rows, each cell 192 by 208 pixels. Each row is one animation and each cell in it is one frame. The app animates an avatar by showing one cell at a time from the row it wants.

| Row | State | Frames | Shown when |
| --- | --- | --- | --- |
| 0 | `resting` | 6 | Nothing is happening, and greyed out when the server can't be reached |
| 1 | `working` | 6 | The agent is running a turn |
| 2 | `replied` | 6 | A reply the person hasn't opened |
| 3 | `failed` | 8 | The last turn failed |

`avatarStateOf` in `contract.ts` picks the state from an agent as the home screen shows it, for the apps and the server alike. Each row also names one frame as its `still`, which stands for the state where nothing can move, as in a Live Activity.

`skills/make-avatar/render.ts` builds every frame from the avatar's `design.json`. Each row applies the same changes to the one grid: eyes open, blinking, looking down, happy or crossed, a hop, a heart or a sweat drop, and grey colours for `failed`. The agent writes `design.json` into `~/.sidebots/avatars/<avatar-id>/`, runs the script, and looks at the result before replying.

The starter avatars live in the repository's `avatars/` folder and are copied into `~/.sidebots/avatars` on the server's first start.

### The providers' programs

Each provider's program is the one installed on the machine. The server looks for it by the command a terminal runs it by, `claude` or `codex`: on the PATH of the person's shell, then on the server's own, then in `~/.local/bin`, where both makers' installers put a program, and in Homebrew's folders. It reads the shell's PATH by starting the shell as an interactive login shell, which reads the startup files that put a person's tools on it, and having it print the PATH between two marks, since those files can print things of their own. The server started by the Mac app has only the system's PATH, so this is how it finds what the person's terminal finds. The programs run with that PATH too, so a launcher finds what it launches.

The server asks the program for its version with `--version`, and remembers the answer until the file changes. Each driver has an oldest version it works with, `oldest` in `PROGRAMS`: 2.1.325 for Claude Code, the version its Agent SDK is made for, and 0.170.0 for Codex. A turn on a provider whose program is missing or older fails with what to do on the computer. A program that isn't found has the shell's PATH read again, at most every half a minute, so one installed since is found without a restart.

Four commands let the Mac app do all of this through the server. `providers` lists each provider's program: where it is and its version when it is installed, whether its driver works with it, the oldest that it does, its maker's installer, and the config folder it uses on the machine. `install <provider>` runs that installer, `curl -fsSL https://claude.ai/install.sh | bash` for Claude Code and `curl -fsSL https://chatgpt.com/codex/install.sh | sh` for Codex, told not to stop and ask. `sign-in <provider> <config-dir>` runs the provider's own sign-in in a config folder, with the command's own input and output, and ends it when the command is told to stop. `signed-in <provider> <config-dir>` says whether that folder is signed in, as whom when the provider says, and whether the login is an API key saved there: Claude Code's `auth status --json` prints whether and as whom, and Codex's `login status` says whether by how it ends, and what with in the words it prints.

### Adding a person

The person who runs the server adds each person once, with a name, a provider and a config folder of their own for it: `pnpm add-person <name> <provider> <config-dir>`, such as `pnpm add-person Alex claude ~/.claude`. The other commands know the person by that name, so each person on a server has a different one. `pnpm add-account <person> <provider> <config-dir>` sets a person up on another provider, and a new agent of theirs runs on the first they set up unless they pick another.

The person's agents then sign in to each provider in one of two ways:

- **A login.** The person signs in to the provider in their config folder themselves.
- **An API key.** The person who runs the server puts the key in a file and saves it with `pnpm api-key <person> <provider> <file-holding-the-key>`. The key comes in a file so that it is never typed into a command the shell remembers. The agents sign in with the key, and nobody signs in to the provider.

The store keeps the keys in `~/.sidebots/api-keys.json`, by person and provider, readable only by the server's user account, as it keeps `machine.json`. A person with a key there runs on it from their next turn, and saving another replaces it. `pnpm api-key <person> <provider> --remove` takes the key away, and the person runs on the login in their config folder again. Both providers use the key ahead of a login, so a key takes over even in a config folder that is signed in. A person with no key runs on the login in their config folder.

A key is in no log line, no response to the phone and no failure notice: if an error from a provider quotes the key, the runner takes it out before the notice is saved. Claude Code gets the key in its environment, so an agent's own commands can read the key it runs on, as they can any file of the server's user account.

### Running a turn

This section and the next say how a turn runs on Claude Code. [A turn on Codex](#a-turn-on-codex) says what differs there.

For each queued message, the runner calls the SDK's `query` once, in its streaming input mode, with:

- `cwd` set to the agent's home folder
- `resume` set to the agent's `session_id`, when it has one
- `pathToClaudeCodeExecutable`, the Claude Code on the machine
- `env` with the PATH of the person's shell, `CLAUDE_CONFIG_DIR` for the person who owns the agent when their folder isn't Claude Code's own, and `ANTHROPIC_API_KEY` when that person has a key
- `settingSources` of `user` and `project`, so the person's skills and connections load along with the agent's `CLAUDE.md`
- `systemPrompt` set to the `claude_code` preset, which is Claude Code's full prompt, with two lines of Sidebots' own added: the one that asks for a `description` with every command, and the one that says when to show something. Without the preset the SDK uses a short prompt that leaves out memory
- `settings` that turn Claude Code's memory on and set its folder to the agent's `memory/`
- `skills: 'all'`
- `permissionMode: 'auto'`
- `canUseTool`, which Claude Code calls for an action auto mode can't decide on, and which asks the person
- `disallowedTools` naming `AskUserQuestion`, so the agent puts its questions in its reply
- `model` and `effort` set to the agent's. Claude Code runs a model that hasn't that effort at the highest it has
- `abortController`, the driver's own, which ends Claude Code's process when a stopped turn doesn't end by itself

Files sent with a message are saved in the agent's `attachments/` folder before the turn, and the prompt ends with their paths. The agent opens them with its ordinary file tools.

The runner sends each message with its Sidebots id as its `uuid` and `priority: 'next'`. The query stays open while the turn runs, and a message the person sends meanwhile goes into it. Claude Code reads it at its next pause between steps. Claude Code sends a `command_lifecycle` frame for each message, and the runner marks a message read when its state is `started`, which for a message sent into the turn is at that pause. A result names the messages its reply answers. The runner saves the reply, marks those messages done, and closes the query once every message sent to it has its reply and no background work the agent started, such as a long command, is still running. The SDK reports that work in `background_tasks_changed`. When it finishes, Claude Code wakes the agent by itself, and the result of that turn names no message: the runner saves it as a reply like any other. The query waits for background work for 30 minutes at most, then closes, which stops it. A follow-up that arrives as the turn is finishing gets a reply of its own in the same session.

The runner stores the session ID from the last result on the agent. A turn ends with its query, so the server keeps no long-lived state and a restart loses nothing. Each agent runs one turn at a time.

When a message answers an earlier one, the prompt starts by quoting it.

### Stopping a turn

The runner keeps an `AbortController` for the turn each agent is running, and gives it to the driver as the turn's `stop`. `POST /agents/:id/stop` aborts it, as deleting the agent does.

Claude Code's driver answers the abort with the query's `interrupt`, the SDK's request to end the turn that is running, with `cancelQueued` set, so that messages sent into the turn and not yet read are dropped instead of run. Claude Code ends the command it was running, writes `[Request interrupted by user]` into the session, and sends a result whose `terminal_reason` is `aborted_streaming` or `aborted_tools`. The driver closes the query once the interrupt is answered and takes the session id from that result, and the query ends within about a second. The session is whole, so the next turn resumes it, and the agent knows it was stopped.

The SDK's `abortController` ends Claude Code's process. A session ended that way resumes too, but it records the command as failed (`Exit code 137`) with nothing to say the person stopped it. The driver ends the process in two cases. One is at once, when the interrupt leaves no turn to end, because no message is left that Claude Code read and hasn't answered, and Claude Code would wait on for one. The other is after 10 seconds, when a stopped turn hasn't ended.

As a stop is asked for, the runner notes the person's messages that the agent hasn't read, those sent into the turn and those waiting for it to end. When the stopped turn ends, the runner stores its session id, adds a `Stopped` message from Sidebots with status `done`, marks the messages the turn had read `done` and the noted ones that are still unread `failed`, and goes on to whatever waits in the agent's queue. A stop that comes as the turn's last reply lands, with no message unread, adds no `Stopped` message. Nor does one that only ends a turn before it read what another agent asked: stopping that agent has already marked the message `failed`, and a reply the turn still gives to it is dropped. A stopped turn notifies nobody, and queues no fresh start however large its session is. An ask it was waiting on closes unanswered, since the interrupt has Claude Code withdraw it. The turn is counted with what its session had cost when it stopped, which the interrupted result says. A stopped job's run sends no reply, and the job moves to its next time as after any run. A stopped fresh start leaves `session_id` as it is and marks its own line `done`. When the agent is being deleted, its queue ends with the stopped turn and writes nothing.

`POST /agents/:id/messages/:message/resend` puts a `failed` message from the person back to `queued`, so it waits its turn as it was sent.

### A turn on Codex

The Codex driver starts the installed Codex as `codex app-server` for each turn, with `CODEX_HOME` set to the person's config folder when it isn't Codex's own, and ends it with the turn. The two speak JSON-RPC over the process's input and output, one message to a line. The driver greets it with `initialize`, asking for the parts of the protocol Codex calls experimental, which the agent's tools and the reviewer are. With an API key, it starts Codex with `cli_auth_credentials_store="ephemeral"` and signs in with `account/login/start`, so the key lives in that process's memory and no login in the folder is read or changed. Without one, it asks `account/read` first, and a folder with no login fails the turn as signed out.

A session is a Codex thread. The first turn starts one with `thread/start` and later turns resume it with `thread/resume`, by the thread id kept as the agent's `session_id`. Both set the agent's folder as `cwd`, the model, `approvalPolicy: "on-request"`, `approvalsReviewer: "auto_review"`, `sandbox: "workspace-write"`, the memory instructions and the line that says when to show something as `developerInstructions`, and Codex's own memory off. The model is the newest of the agent's kind in what `model/list` answers. A job's run starts a thread with `ephemeral: true`, which Codex doesn't keep.

The agent's tools go to Codex as `dynamicTools` on `thread/start`. Codex asks the driver to run one with `item/tool/call`, and the driver answers with the tool's words. A thread keeps the tools it started with, so it starts with them all, and `send_update` answers that nobody is waiting in a turn that has none. A tool that reads the machine's files runs as it is called, as `send_files` does, since Codex's sandbox lets an agent read anywhere. Codex's reviewer judges only what an agent runs on the machine, so before a tool acts as the person outside it, as sending a mail does, the driver asks the person, with the tool's name in words and what it was given.

A message starts a turn of Codex's with `turn/start`, under its Sidebots id as `clientUserMessageId`. A message the person sends meanwhile goes into that turn with `turn/steer`, under its own id, and Codex hands it to the agent at its next pause between steps. Codex tells of each message as the agent reads it, in a `userMessage` item that names the id, and the driver marks it read. When `turn/completed` comes, the reply is the agent's last message that isn't commentary on its work, and it answers every message read in the turn. Codex refuses a message steered into a turn that is ending, and the driver starts another turn with it in the same thread, so it gets a reply of its own. The effort goes with each `turn/start`: the agent's, or the highest among the model's `supportedReasoningEfforts` in what `model/list` answers when the model hasn't the agent's, as Luna has no ultra.

Codex's reviewer decides on what the sandbox won't allow, so those actions never reach the person. When it refuses one, the agent is told and says so in its reply. What Codex asks its client instead, `item/commandExecution/requestApproval` and `item/fileChange/requestApproval`, the driver turns into an ask for the person, and answers `accept` or `decline`. Codex takes no words with the answer. Anything else Codex asks is refused, so it never waits.

A stop sends `turn/interrupt`. Codex ends the command it was running, records in the thread that the turn was interrupted, and sends `turn/completed` with status `interrupted`. The thread is whole, so the next turn resumes it. The driver ends Codex's process when a stopped turn hasn't ended after 10 seconds. A new thread that was stopped before its first turn began is not kept as the session.

Codex says how many tokens a thread has used in `thread/tokenUsage/updated`, from the thread's start and on its last step, and says the count again as it resumes a thread. The last step's count is how much the session holds. Codex counts tokens and says nothing of money, so the driver prices them at OpenAI's API prices for the agent's kind of model, apart for tokens read, read from the cache, written to it and written as the answer. Each count names the turn it stands after. The tokens a run used are the count as the run ends, less the count Codex said as it resumed the thread, which names a turn from before the run. The driver prices those at the model the run was on and adds them to what the session had cost before, which the runner hands it from the last turn the store recorded there. That is the session's total cost, which the store handles as it does Claude Code's, so a session that changes model part way costs what each of its turns did. The run's tokens, by the count's `totalTokens`, go the same way: added to what the session had used before, they are the session's total.

On a plan, Codex sends `account/rateLimits/updated` as a turn runs, with up to two windows of the plan's limit: how much of each is used, how long it runs, and when it resets. The driver names each for how long it runs, as "5-hour limit" or "Weekly limit", and leaves out a limit that one model has apart from the plan's. Asked with `account/rateLimits/read`, in a process that starts no thread, Codex answers with the same windows for every limit by its id, and the driver takes the plan's own, `codex`. A login can be an API key the person saved with `codex login --with-api-key`, which has no plan. The driver asks `account/read` first, and says so in place of limits.

When an agent is deleted, the driver lists the threads that ran in its folder with `thread/list` and removes each with `thread/delete`.

### Updates during long work

For a turn the person is waiting on, the runner gives the agent a `send_update` tool. Its description tells every agent to use it only when work takes a long time, to say in a sentence or two what is done and what is left, and not to repeat it in the final reply. The server enforces the timing: an update in the turn's first minute, or within three minutes of the last, is refused with words telling the agent to carry on. An update is saved as a message from the agent with `interim` set.

### Files from the agent

The runner gives each agent a `send_files` tool, which takes the paths of files on the machine, in full or from the agent's home folder. The store reads each file as the tool is called, so what the person gets is the file as it was then, whatever the agent does with it after. The files wait in the turn for the agent's next message, which is its reply, or an update that comes first. The store writes them into `attachments/` under names of their own as it saves that message, as it does the person's, and the message lists them in `attachments`, so the app draws and fetches them the same way. A call that names a path with no file, or that would bring a message's files to more than 95 MB, adds none of its files and tells the agent why. The tool reads with the server's permissions, so Claude Code's safety check judges each call to it, as it does the agent's own actions. The agent's tools that neither read the machine's files nor act as the person outside it always run. A job's run has the tool too: its files go with its reply, and nowhere when the run stays silent.

A page is a file the agent sends whose name ends in `.html`. The tool's description tells every agent to write one as a single file that fits a phone's width and wider ones, with any picture inside it or left on the web at an https address, and names the colours it is given. It says the chat shows the file's name above the page as its title and the top of a long page, so the agent names the file as a title, gives the page no title or outer space of its own, and puts what matters first. When to send one is in the agent's prompt, since an agent reads a tool's description only once it has thought of the tool: the runner adds a line to every provider's own prompt that has the agent show what is better seen than read, numbers as a chart, things to choose between as a page with a card for each, and a picture when the person asks what something looks like, and keep a plain answer to words. A session keeps the prompt it began with, so a chat that is already going takes the line up at its next fresh start. The app fetches the page's text as it fetches any attachment and draws it in a web view, from `react-native-webview`, as a document of no site: it holds none of the phone's keys, keeps nothing between openings, and is refused the camera and the microphone. Before the page's own content loads, the app gives it the chat's colours as its background and text and as the CSS variables `--bg`, `--ink`, `--ink2`, `--line`, `--field` and `--tint`, and gives them again when the phone moves between light and dark. The page tells the app how tall its content is, which sets its height in the chat between 60 and 480 points. No address replaces the page. A web link opens in the Safari sheet, and only just after the person taps the page, so neither a page's own script nor a scroll opens one. Where a tap leads is the page's to say, as it is a link's in a reply. Any other address is refused, a place further down the same page included. Its scripts run, and it may fetch from the web. An HTML file the person sends stays a file, as it is to the agent. A page the phone can't fetch shows as its file card.

### Asking before an action

When auto mode can't decide on an action, Claude Code calls the driver's `canUseTool` with the tool and what it was given, and waits. The driver turns the call into a question, `Question` in `contract.ts`, in the parts a person reads to decide:

- `kind` and `title`: what sort of thing it is, a command, a page, a file or another tool, and that in words. An ask for a [connection](#connections) is a kind of its own, which the runner raises.
- `what`: this one thing in plain words. A command's is the `description` Claude Code lets an agent give with a command, for a person who won't see the command. An agent skips it unless told, so the driver adds a line to Claude Code's prompt that asks for it with every command. Nothing checks it against the command, and a command that comes without one leads with its own first line. A page's is its site, a file's its name, and another tool's its own name in words.
- `facts`: the short details that matter, each a label and a value. A page's is what the agent looks for there, a file's its folder and the size of the change, and another tool's the short values among what it was given.
- `detail`: the thing itself, whole, since Allow lets all of it happen. A command is its text, a page its address, a file its path with what would be written or changed, and another tool what it was given.
- `why`: Claude Code's reason for asking, when it gives one.

The runner saves the question on a message from the agent with `ask` set to `waiting`, which notifies the phone as a reply does, and keeps the turn waiting on it. The message's `body` says the question in words, with its detail, for a search and for an app that doesn't draw the card. The phone draws the card from the question, with the detail behind a tap, and a notification or the chat list shows its title and plain words.

`POST /agents/:id/asks/:message` brings the person's answer, which for a connection can only be no. The message's `ask` becomes `allowed` or `refused`, the person's devices hear of it over the event stream, and the runner hands the answer to the driver, which answers Claude Code: go on, or leave it, with words for the agent on what to do instead. An ask takes one answer, and a second gets 409.

An ask closes as `unanswered`, and the action is left undone, when half an hour passes, when the person sends a message that goes into the turn, when Claude Code withdraws the call, and when the turn ends for any reason, as when it fails or its agent is deleted. The asks a stopped server left waiting are closed when it next starts, as their turns are queued again. An answered ask notifies nobody.

### Connections

A connection is an app outside Sidebots that a person's agents use as that person. `CONNECTIONS` in `contract.ts` names each, with the name the apps show, its logo and what connecting it allows. A logo is one shape in a box 24 by 24, as Simple Icons draws a brand's mark, with the brand's colour, and the server sends it with the rest, so the app draws a connection it has never heard of. The `connections` module holds the rest: for each connection, whose app it is, what its sign-in asks that maker to allow, and its tools, or the address of the server its maker gives them from; and for each maker, how a person signs in.

An app's tools come one of two ways. Notion runs a server that gives its tools, as MCP, so Sidebots has none for it: a turn is handed the server with a token, and the provider reads the server's tools and uses them, as it does for any MCP server. Google's servers for Gmail and Google Calendar are in a Developer Preview that a project has to be let into, and its Gmail server sends no mail, so those two have tools written in the `connections` module, which ask Google's APIs.

Signing in is OAuth's authorization code flow with PKCE, which is how an app that can keep no secret signs in, so the server swaps the code for tokens itself and no server of Sidebots' sees them. `POST /connections/:id/sign-in` makes a `state` and a secret, the verifier, keeps them for ten minutes, and answers the address of the maker's page, which carries the client id this Sidebots signs in with, the scopes, the `state` and the verifier's SHA-256 hash, and the address the page goes to once the person has signed in. For Google that is the address Google gives an iOS app's client, the client id turned about, as in `com.googleusercontent.apps.<id>:/oauth2redirect`. For Notion it is `app.sidebots:/oauth2redirect`. The phone opens the page in `ASWebAuthenticationSession`, the sheet iOS has for signing in, which hands the app the address the page ended on. The desktop app opens the page in the system browser, which hands that address back to the app registered for it, as `docs/specs/2026-11-21-desktop-app.md` says. `PUT /connections/:id` brings that address. The server finds the sign-in by its `state`, which works once and only for the person who started it, and sends the code with the verifier to the maker's token address. The maker hands tokens only to whoever holds the verifier, so a code read off the phone is no use to anyone else. Google lets a person untick part of what a sign-in asks for, and a sign-in that granted less than the connection needs makes no connection.

The store keeps what lasts in `~/.sidebots/connections.json`, by person and connection, readable only by the server's user account: the account that signed in and the refresh token. Google names the account in its id token. Notion names the workspace the person signed in to, in `workspace_name` beside its tokens, and the connection is listed as that. The token the app is asked with lives in the server's memory. One with less than half an hour left is replaced with the refresh token before it is used or handed to a turn. A maker has ten seconds to answer. A maker may answer with a new refresh token, which ends the one before it, and the store then keeps the new one. Those that ask at once wait for one new token between them, so no second request is made with a refresh token that the first has ended. When a maker answers `invalid_grant`, the person has taken the connection back at the maker's or the maker has ended it, and the module forgets the connection. It also forgets one whose maker renews it with less than the connection needs, as for a sign-in that asked for less, and the tool tells the agent to ask the person to sign in again. `DELETE /connections/:id` forgets one too, and a turn that is running keeps the token of a server it was handed until it ends. Gmail and Google Calendar are connections apart, each with its own sign-in and token, so a person can have one without the other.

The client id for Google is the Sidebots app's own, which `main.ts` names, or a build of one's own from `SIDEBOTS_GOOGLE_CLIENT`. It is the id of a client of the type iOS in a Google Cloud project, made for the app's bundle identifier, which has no secret. The project is published but not yet verified by Google, so Google's sign-in page warns that it hasn't verified the app, and it signs in at most 100 people. A sign-in to an app whose maker has no client id answers that Sidebots isn't set up for it.

Notion hands out no client id. Its client id is the address of a file, `https://sidebots.app/oauth-client.json`, in `site/public`, which is how MCP has a client name itself (a Client ID Metadata Document). The file says the client's name, that it keeps no secret, and the one address a sign-in may come back to, and Notion reads it as the person signs in. That address belongs to no one app, since `ASWebAuthenticationSession` hands the address a page ended on to the app that opened it, so every build signs in with the same file. Every request for Notion's tokens also names the server they are for, `https://mcp.notion.com/mcp`, as `resource`.

As a turn starts, its driver asks the runner for the person's servers, `servers` in the `connections` module: the address of the server of each connection they have made whose maker runs one, with a token. A connection whose token can't be had is left out of the turn. Claude Code's driver gives each server to the Agent SDK in `mcpServers`, as a server of the type `http` with the token in its `Authorization` header, under the connection's id. Codex's driver names each in the thread's `config`, as `mcp_servers.<id>` with a `url` and the header in `http_headers`, on `thread/start` and `thread/resume`. An ask from Claude Code about one of a server's tools names the connection as the apps do.

The runner gives every agent a `connect` tool and the tools written here for a connection, whether or not the connection is made, since a Codex thread keeps the tools it started with. A table change gives the Codex sessions that began without them a fresh start. A tool of a connection that isn't made answers that it isn't connected and names `connect`. `connect` asks the person with a `Question` whose `kind` is `connection` and whose `connection` names the app, and waits as any ask does. Making the connection answers every ask that waits for it, in whichever chat, and "Not now" answers the ask no. The tool then tells the agent which account is connected, or that the person said no. When the connection is to an app whose maker serves its tools, Claude Code's driver then hands the query its servers again, Sidebots' own tools and the person's connections, with `setMcpServers`, so the agent has the app's tools in the same turn. A Codex thread reads its servers as it starts or resumes, so an agent on Codex has them from its next turn.

Gmail's tools are `gmail_search`, `gmail_read` and `gmail_send`, on the scopes `gmail.readonly` and `gmail.send`. A search answers 25 mails at most, each with who it is from and to and whether it is a draft that isn't sent, and says so when more match. Gmail reads a day in a search, as in `after:2026/11/20`, as one that starts at midnight in California, so the search goes to Gmail with each such day as the instant it starts by the machine's clock. A mail is read as its plain text, every part of it, or as the words of its page when it has none, where a link keeps the address it goes to. It names where it asks for answers to go. A mail that answers another takes that mail's subject and names it in its headers, which is what keeps the two in one thread.

Google Calendar's tools are `calendar_events`, `calendar_event`, `calendar_list`, `calendar_add_event`, `calendar_change_event` and `calendar_remove_event`, on `calendar.events`, which reads and changes the events of any calendar, and `calendar.calendarlist.readonly`, which reads which calendars the person has. A look reads every calendar the person has ticked in Google Calendar, their own and each one they made, follow or were shared, and answers the events of them all as one list, earliest first, with their times by the machine's clock. An event that two calendars have, as one the person is a guest of, is told once, as the person's: every copy of an event has its `iCalUID`. Google reads a whole day by the clock of the calendar it is on, so a look keeps only the whole days that fall in it by the machine's clock. A calendar that can't be looked at is left out of the look, which says so. A look that names a calendar reads that one alone, ticked or not, and one that finds nothing says so and names the calendars it didn't look at. `calendar_list` lists the person's calendars, each with whether it is ticked and whether its events can only be read. An event on a calendar that isn't the person's own names the calendar and its id, and says when the calendar can only be read. The other tools take a calendar by that id or by its name, and act on the person's own calendar without one. An event in a look has the start of its notes and the link to its call when Google keeps one, one that repeats says that it is one time of it, and `calendar_event` reads one event with all its notes, which is where the link to join a call often is. Google marks as `self` the guest whose calendar an event is on, so a guest is told as the person only on the person's own calendar. An agent writes a time by the machine's clock, and a day alone is an event that takes whole days. A look answers 50 events at most, and says so when the calendars have more. A tool that changes something or speaks as the person is marked as one that acts: sending a mail, and adding, changing or removing an event. Claude Code's safety check judges each call to one, as it does a call to `send_files`, and on Codex the driver asks the person. What an app refuses, the tool tells the agent in the app's words.

Adding a connection takes an entry in `CONNECTIONS` and one in `APPS` in the `connections` module, with its maker, its scopes and the address of its maker's server. An app whose maker runs none, or none that will do, has tools there in its place, and a table change like the one above, for the Codex sessions that began without them. A tool that is added to a connection, or takes something new, needs such a table change too. A new maker also takes an entry in `MAKERS` and its client id in `main.ts`. The apps list connections by the names the server sends, so they need no change.

### Agents asking each other

The runner gives each agent two tools for the person's other agents: `list_agents`, which names them, and `ask_agent`, which takes a name and a message. A message one agent sends another is a row in `messages` like any other, written by the asking agent with `sender = 'agent'`, with the other agent in `peer_id`. It waits in that agent's queue with `status` as a person's message has it: `queued` until the other agent reads it, `running` while it works on it, then `done`, or `failed` when it got no answer. The tool answers at once, and the asking agent's turn ends.

The other agent reads the message in a turn of its own, in its chat's session, told which agent sent it and that its reply goes back to that agent. The reply is saved as its own message with the asking agent in `peer_id` and the message it answers in `reply_to`, and waits in the asking agent's queue, where it starts a turn that says who answered and what was asked. A turn for another agent's message takes no message of the person's into it, as a job's run doesn't.

So no agent holds a turn open while it waits, and two agents that ask each other can't lock. Each turn's reply goes to whoever it is owed, which `deliver` in the runner decides as the reply comes:

- While the agent has asked something it hasn't heard back on, its answer is still to come, so the reply goes to the person as an update, with `interim` set.
- Otherwise, when another agent's message is still unanswered, the reply answers it.
- Otherwise it goes to the person.

A turn that fails while working on another agent's message answers that agent with why. An approval ask raised while an agent owes another agent a reply carries that agent in `peer_id`.

A chat lists the rows whose `agent_id` or `peer_id` is its agent, so an exchange is in both agents' chats from one set of rows, and the event stream sends such a row once for each of the two agents. `exchanges` in the contract groups a chat's rows into the exchanges it shows a line for. `latest` and `unread` leave out what agents say to each other, and no notification is sent for it. An agent's row carries `waiting_on`, the agent it asked and hasn't heard back from. Stopping an agent stops the agents working on what it asked, and marks what they hadn't read `failed`. Deleting an agent removes what other agents said to it, and the event stream sends each of those agents after it, as it now stands.

Nothing in code limits how long two agents go on asking each other. Each turn is the agent's own choice, and Stop ends it.

### Jobs

The runner gives each agent three tools beside `search_history`: `schedule_job`, `list_jobs` and `cancel_job`. A job is what to do on each run, written by the agent to itself, and a schedule. Times are the server machine's local time, and the tools' answers tell the agent the time now.

A clock in the server looks every 15 seconds for jobs whose time has come and starts their agents' queues. An agent's queue runs the messages it was sent first, then any job that is due, one turn at a time, so a job never runs alongside a reply in the same folder.

A job's run is a new session that is not saved (`persistSession: false`), on the agent's model, in the agent's folder. It never touches the chat's session, so a job that runs every few minutes doesn't fill it. The prompt gives the run the job's instructions, tells it to keep what the next run needs in memory, and tells it to reply with only the word `SILENT` when there is nothing worth telling. Any other reply is saved as a message from the agent, with the job's id, and notifies the phone. The chat's session never saw that message, so the person's next message carries what the jobs sent since the agent's last reply: the latest 20, and when there were more, a line that says so and points the agent to `search_history` for the rest.

After a run, an interval counts from the end of the run, a daily job moves to its next day, and a job set for one time is removed. After the machine has been asleep or off, each job that was due runs once. A run that fails adds a failure notice to the chat, unless the latest message there is already one.

### Counting usage

Every result Claude Code sends carries `total_cost_usd`, its own estimate of what the session has cost at Anthropic's API prices, with the agent's subagents counted. For a session that is resumed, that total starts from the turns before. The result's `modelUsage` counts the session's tokens the same way, a model at a time: the ones read, read from the cache, written to it and written as the answer. Their sum is the tokens the session has used. So the driver hands back the session's totals, and the store works out the turn's part of each: the total, less the total after the last turn recorded in that session. A job's run is a session of its own, so its totals are its own. The first turn recorded in a session that already had turns counts as using nothing, since nobody can tell how much of the total is its own. The same goes for tokens on the first turn after one that was recorded without them. A turn that fails is not recorded. In the chat's session what it used falls to the next turn that succeeds there. Each turn is a row in `usage`, with its agent and whether it was a reply, a job's run or the memory save before a fresh start.

On a plan, Claude Code sends a `rate_limit_event` as a turn runs, with where the plan's limits stand: the 5-hour and weekly limits, and the limits a plan has for Opus, Sonnet or Fable alone. Each comes with the part of it that is used and when it resets, and has the name Claude Code gives it in its own messages. The event names one limit, the one the turn is nearest or has reached, and lists the main ones in `unifiedWindows`, which the SDK's published types leave out. The driver passes on both, and counts a limit that refuses the turn as all used. The driver hands the limits to the runner as they come, so a turn that fails because a limit is reached still records it. The store keeps the latest word on each limit in `limits`, by person and provider. A limit whose time to reset has passed is left out until Claude Code speaks of it again.

The event leaves out a limit the turn is far from, such as Fable's when the turn runs on another model, and says nothing between turns. So the driver also asks. It opens a session that is sent no message, so no turn runs and nothing of it is kept, and makes the SDK's usage request with `skipBehaviors`, which leaves out a read of the sessions on the computer. The answer lists the 5-hour and weekly limits, the Opus and Sonnet ones, and in `model_scoped` each limit one model has apart from the rest, under the name Anthropic gives the model. Each comes with the part of it that is used, out of a hundred, and when it resets. A login with no plan gets none. The SDK marks the request as one that may change, and a Claude Code that stops answering it leaves the limits to the event.

`GET /usage` first asks each provider the person is on a plan with where the plan's limits stand, and keeps the answers in `limits`. It asks a provider once a minute at most and gives it five seconds to answer, half as long as the phone waits for the page. A request that comes while a provider is being asked waits for that answer. One that fails or is late leaves what it last said. The seven days are today and the six before it, each from midnight on the computer and named by its date there. It then answers with the person's turns of those days, added up by agent and by what they were for, and again by day, and, for each provider the person has set up, whether they are on an API key or else the plan's limits. A person is on an API key when they gave Sidebots one, or when the provider just said the login in their config folder is one.

### Replacing a session

A session is replaced when the person asks for a fresh start, or when a turn ends with the session holding more than 120,000 tokens. The size comes from the usage on the agent's last step, which counts everything the model read for it.

A fresh start is a message from Sidebots that waits in the agent's queue like any other, so it runs after the turns ahead of it. The runner first runs one turn asking the agent to save what is worth keeping to its memory, and then clears `session_id`. If that turn fails the session is replaced anyway, since the chat is still there to search. The next turn starts a new session whose first prompt includes the 20 most recent messages from the database.

### Pairing a phone

`pnpm pair <person>` makes a pairing code and prints it as a QR code and as a link, with the address the phone reaches the server at. That is the machine's own address, unless `--host <address>` names another, such as the machine's Tailscale name. The code is 32 random bytes. The store keeps only its hash, with the person it is for and when it expires: ten minutes later, or as many days later as `--days <n>` says.

The QR code holds one link:

```
sidebots://pair?host=<address>&code=<code>
```

The phone sends `POST /pair` to that host with `Authorization: Pairing <code>`, its contract version in `Sidebots-Contract`, and its own name. The server refuses a phone on another version, or one that sends no version, before it looks at the code. Otherwise it checks the code, deletes it, and answers with a device key and a notification key, each 32 random bytes, and the machine's name for the app to show. The phone sends the key on every later request as `Authorization: Bearer <key>`. The store keeps the key's hash, never the key. The api matches each request's key to a paired device and its person, and answers 401 to a request with no known key. A phone whose app was deleted and installed again still has its old device key, because the Keychain outlives the app. As it pairs, it sends that key's SHA-256 hash, in hex, as `replaces`, and the server deletes the pairing with that hash, so the phone is listed once. The hash is what the store keeps of the key, and no server lets a phone in for it. A device names its `kind` as it pairs, `phone` or `desktop`, and one that names none is a phone.

`pnpm devices` lists the paired devices, each with its kind, and `pnpm remove-device <id>` deletes one, so its next request gets 401. `pnpm status` says whether a server answers on the port and at the machine's address, how each person's agents sign in, and whether the server tells the relay how much it is used. With `--json`, `status`, `devices` and `pair` print JSON for the Mac app and the desktop app. The server and these commands open the database at once, so each waits up to five seconds for the other's lock.

### Looking at past messages

One search in the store finds the messages that contain a word or phrase, across all agents that belong to the same person, newest first. The runner gives it to each agent as a `search_history` tool, built with the SDK's `createSdkMcpServer` and `tool`. The app's search field reaches it through `GET /search`.

### The relay and the tunnel

The relay is a Cloudflare Worker in `relay/`, at `relay.sidebots.app`. It gives each machine its address and tunnel, and passes the server's notifications to Apple, since only the Apple Developer account that built the app can notify it and the relay holds that account's push key. `SIDEBOTS_RELAY` names the relay, and is `https://relay.sidebots.app` unless set. With `SIDEBOTS_RELAY=off` the server registers nowhere, runs no tunnel and sends no notifications, and everything else works.

The server registers with the relay when it starts, and again once a day. The first time, it makes an Ed25519 key pair and keeps the private key in `~/.sidebots/machine.json`, readable only by the server's user account. It sends the public key and its port to `POST /machines`, with how much it is used: the version of the Mac app it runs in, how many agents and paired phones it has, and how many turns its agents ran on each of the last seven days, by provider and kind of turn. `pnpm counts off` has it send the key and port alone. For a new key, the relay makes a Cloudflare Tunnel whose requests go to `http://127.0.0.1:<port>` on the machine, and a DNS record that points `<machine id>.sidebots.app` at it. It answers with the machine's id, the address and the tunnel's token, which the server keeps in `machine.json`. A key that is already registered gets the same machine and tunnel back. The relay lets one network address register three new machines a minute, through the Workers rate limiting binding.

The tunnel module runs `cloudflared tunnel run` with that token, from `SIDEBOTS_CLOUDFLARED` or the `PATH`, and starts it again ten seconds after it stops. It starts on the token the machine kept, so the phone reaches the machine while the relay can't be reached, and moves to a new token when a registration brings one. A custom rule on the `sidebots.app` zone, set by `relay/zone-rule.ts`, blocks any request to a machine's address that carries no `Authorization` header, and leaves the relay, the zone's own name and `www` alone. The phone sends one with every request.

Every request to the relay carries `Authorization: Signature <machine>:<time>:<signature>`, where `machine` is the id, or the public key when it registers, and the signature covers the method, the path, the time and the body's hash. The relay refuses a request whose time is more than five minutes from its own. `DELETE /machines/:id` removes a machine, its tunnel and its address, and only that machine may ask. A daily run removes the machines the relay hasn't heard from in 60 days in the same way. A removed machine registers again with the key it has, and gets a new address, so each phone pairs again. The relay keeps each machine's public key, id and tunnel, and how much the machine says it is used, and nothing about who anyone is or what was said.

### Notifications

`POST /notifications` on the relay takes a notice: the phone's token, its push service, and one of an encrypted notification with its message id, word that something was read, or the end of a Live Activity. It answers `sent`, `gone` or `failed`. The relay sends a machine at most 1000 notices a day.

The relay can't read a notification. The server encrypts each notice, the agent's name, what it said, the count for the app's icon and the agent's id, as JSON with AES-256-GCM under the phone's notification key: the 12-byte nonce, the encrypted JSON and the 16-byte tag, in base64. The relay sends Apple an alert that says "Sidebots" over "New message", with `mutable-content` set, the message id as its collapse id, and the encrypted notice beside it. On the phone, the notification extension in `mobile/targets/notifications`, the small program iOS runs as a notification arrives, reads the key from the Keychain group it shares with the app, opens the notice, and shows the agent's name over what it said, with the count and the agent's thread. When it can't, the notification shows as the relay sent it.

The app gives the server its device token once the person allows notifications, and again on each return to the app. The server sends a notification when an agent's reply is saved, when an agent asks before an action, and when a turn fails, unless the agent is muted. It waits two seconds first, `NOTIFY_AFTER_MS` in the contract, and sends only what is still unread then: the device the person is reading the chat on marks it read well within that, so no phone sounds for it. The desktop app holds its own notifications by the same rule. An update during long work sends none. Each one carries the number of replies and failure notices the person hasn't read across their agents that aren't muted, which the app's icon shows, and the sound `sidebots.wav`, which the app carries in its bundle. When Apple says a token is no longer in use, the server forgets the token, and the phone stays paired.

An agent's unread count is its replies, asks and failure notices newer than its `read_at`, not counting updates during long work. A chat is read while the person looks at it: the phone marks it while the chat is open with the app in front, and the desktop app while the chat is open in the window in front and the person is at the computer. Either sets `read_at` through `POST /agents/:id/read`, and the event stream carries the agent to every device, which clears the count on each.

When that leaves an agent nothing unread, or the agent is deleted, push sends each of the person's phones that it notified a notice that says only `read`. The relay passes it to Apple as a background push, with `content-available` set and nothing else, so it names no chat and shows nothing. iOS wakes the app, which asks the server for the agents and takes off the phone the notifications of every agent with nothing unread, of those that came before it asked. The app does the same whenever the event stream says how the agents stand, and sets the count on its icon then. Apple delivers background pushes when it suits the phone, and none to an app the person has quit, so a notification can stay until the app is next opened.

### Live Activities

A Live Activity is the card iOS keeps on the Lock Screen and in the Dynamic Island for work in progress. Apple's ActivityKit splits what an activity shows in two: attributes, set once when it starts, and a state, which is all an update can change.

The app starts an agent's activity, and the server ends it. The app starts it because iOS starts one without a sound only for the app in front, and because the app can then set the attributes itself: the agent's name, its avatar's picture in each state, the line under the name in each state, the link a tap opens and when the activity began, which its clock counts from. None of those ever leave the phone. The state is one of the avatar's states, and it starts as `working`.

The app keeps the activities in step with the agents each time the server says how they are, in an event of the stream or as the app catches up: an agent that is working, and not muted, gets an activity if it has none, and an activity whose agent has stopped is taken away. It does this only while it is in front. The picture for each state is the row's `still` frame, cut from the spritesheet the app has saved and shrunk to one pixel for each pixel of the drawing, 16 by 17, since an activity's attributes and state hold 4 KB together.

Apple gives each activity a token of its own, which updates to it are sent under. The app sends it to `PUT /agents/:id/activity-token`, with the push service and the app's identifier as for a device token, and again if Apple changes it. An activity outlives the app, so an app that starts while one is up sends its token again. The server keeps it in `activities` and refuses it when it could never use it: with 409 when the agent has no work left, and with 501 when the server runs without a relay. When the server doesn't take a token, for those reasons, because it is too old to know the route or because it is out of reach, the app ends the activity, since nothing else could.

Whenever a message is added or changes status and its agent has no turn queued or running, push ends that agent's activities: it takes their tokens out of `activities` and sends each to the relay's `POST /notifications` as `ended`, with the state `avatarStateOf` gives, `replied`, `failed` or `resting`. The relay sends Apple an `end` event whose state is that one word, under the topic `<app identifier>.push-type.liveactivity`. `replied` and `failed` stay on the Lock Screen for 15 minutes. `resting` means there is nothing to show, as after a fresh start or a turn the person stopped, and goes at once. An agent that waits on an ask is still working, so its activity stays. iOS takes an ended activity out of the Dynamic Island straight away, so the replied and failed poses show on the Lock Screen only.

The relay and Apple learn that one of a machine's agents has finished, and whether it replied or failed. They don't learn which agent, its name or anything it said. An ended activity needs one push, so a turn costs the phone one, well inside the budget Apple keeps for an app's Live Activity pushes. A relay too old to know `ended` refuses it, and the activity keeps its working pose until the person opens the app, so a relay is updated before the app that starts activities.

An activity lasts as long as the turn does, up to the eight hours iOS allows. A turn that begins while the app is closed, as when its message came from the person's other phone, shows no activity. Apple can start one by push, but only with an alert that lights the screen, and a phone whose app the person has swiped away never hands over the token to end it with.

### API

| Route | Purpose |
| --- | --- |
| `GET /status` | Nothing. An answer says the server is up, and a refusal that it doesn't know the key that asked |
| `GET /agents` | The person's agents with their latest message, their unread count and their chat's count of changes |
| `POST /agents` | Create an agent, on the provider it names among those the person has set up, or the first they set up |
| `PATCH /agents/:id` | Change an agent's name, avatar or colour, what it answers with (its provider, model, effort and speed), or whether it is muted or hidden |
| `DELETE /agents/:id` | Remove an agent and everything it had |
| `GET /agents/:id/about` | The agent's instructions, memories and jobs |
| `DELETE /agents/:id/jobs/:job` | Remove one of the agent's jobs |
| `GET /agents/:id/messages?after=<message-id>` | The newest page of messages, everything after a known message, or with `before=<message-id>` the page before one |
| `POST /agents/:id/messages` | Send a message, as a form with `body`, any `files`, and `replyTo` for the message it answers, up to 95 MB in all, under the 100 MB Cloudflare takes in one request. Text alone can be JSON |
| `POST /agents/:id/messages/:message/resend` | Send again a message the agent never answered, as it was sent |
| `GET /agents/:id/attachments/:name` | A file that was sent with a message |
| `POST /agents/:id/read` | Mark the chat read up to now |
| `POST /agents/:id/fresh-start` | Replace the current session |
| `POST /agents/:id/stop` | Stop the turn the agent is running |
| `POST /agents/:id/asks/:message` | Answer an agent's ask, with `allow` as true or false |
| `GET /connections` | The apps the person's agents can use as them, each with its name, what connecting it allows, and the account it is connected as |
| `POST /connections/:id/sign-in` | Start the person's sign-in to a connection, and answer the page the app opens and the address that page comes back to |
| `PUT /connections/:id` | Make the connection, from `url`, the address the sign-in's page ended on |
| `DELETE /connections/:id` | Forget the connection |
| `GET /search?text=<words>` | The messages that contain the words, in any of the person's chats |
| `GET /usage` | What the person's agents used in the last seven days, by agent and by day, and what is left of their plan |
| `GET /avatars` | The avatars on the server |
| `GET /avatars/:id/spritesheet` | An avatar's spritesheet |
| `POST /pair` | Pair a device that brings a pairing code, a phone or the desktop app, and give it its key |
| `PUT /push-token` | Say where Apple delivers the phone's notifications |
| `PUT /agents/:id/activity-token` | Say where Apple delivers to the Live Activity the phone shows for the agent |
| `DELETE /device` | Unpair the device that asks |
| `GET /events` | Live stream, as server-sent events. Each event is a message that was added, changed status or had its ask closed, with its agent as the home screen shows it; an agent that was added or changed, the same way with no message; or the id of a deleted agent, followed by each agent it had talked with. The server pings the stream every 25 seconds, which is how an app tells an open stream from one that dropped |

Every route but `POST /pair` takes a paired device's key and only returns that device's person's agents and messages.

An app catches up each time its event stream opens. It asks `GET /agents`, where each agent carries `chat_changes`: a count that triggers on the `messages` table raise with every message added, changed or removed in the agent's chat, and in both chats for a message between two agents. The app keeps the count each chat it holds was caught up at, and fetches the newest page of only the chats whose agent has another. While the stream is open, a message that lands in a chat as the one change since that count moves the count on, and a message from a change up to that count is left as the page has it. Any other change to the count, as a message the chat has no place for or an agent that comes with a new count and no message, leaves the chat to be fetched when it is next opened. A page short of a full one is the whole chat, and takes the place of everything the app had of it.

Every response, a refusal included, carries the server's `CONTRACT_VERSION` from `contract.ts` in the `Sidebots-Contract` header. The number goes up when a change means an older app or server can't work with a newer one. The app compares it with its own and uses nothing a server on another version says. A server that sends no header counts as older. The app sends its own version in the same header, and the server refuses to pair an app on another version.

### Phone app

The app lives in `mobile/` and uses Expo Router, where each file under `src/app` is a screen. It has five screens and seven sheets: welcome, pairing, home, the chat and the camera, and the sheets for a new agent, an agent's model and effort, an agent's page, a note opened from that page, an exchange between two agents, usage, and connections. The same app runs on iPad, which turns every way while the iPhone stays upright. A screen sizes itself from the window, never the device (`mobile/src/lib/layout.ts`). A window at least as wide as an iPad held upright splits: the agents' list, which is the home screen on an iPhone, takes a column at its left, and the chat the rest, with a chat opened from the list taking the place of the one before it. A wider chat keeps its messages and composer to Assist's 832pt reading column, centred. Photos come from `expo-image-picker`, the camera and the pairing screen's scanner from `expo-camera`, files from `expo-document-picker`, notifications from `expo-notifications`, and the web view that draws a page an agent sends from `react-native-webview`. The + menu and the chat's menu are the system's own menus, drawn by a small native module in `mobile/modules/message-menu` copied from Assist: a clear iOS menu button laid over what the person taps. The swipes on a row of the home screen and on a message come from `react-native-gesture-handler`. The side menu is `react-native-drawer-layout`'s drawer around the stack of screens, set up as Assist's is, with a second small module copied from Assist, `mobile/modules/side-menu-swipe`, that has the home screen's list wait to scroll until the menu's swipe has judged the drag. The keyboard moves the message field through `react-native-keyboard-controller`, which follows the keyboard on the UI thread, frame by frame. The playful lines shown while an agent works are a list in `client/`. An avatar view takes a spritesheet and a row and draws the frames in turn, and the app caches spritesheets on the phone. A working agent's Live Activity is started and ended by a third small module, `mobile/modules/agent-activity`, over Apple's ActivityKit, and drawn in SwiftUI by the widget extension in `mobile/targets/activity`. The two build the same file for the activity's attributes, so they can't describe it differently. An iPad app in a window of its own has the window's controls at its top left, and a fourth small module, `mobile/modules/window-controls`, measures the room they take there from iOS's safe area adapted to the window's corners, so the buttons at the top left of each screen move aside for them. The app keeps a local copy of agents, the newest page of each chat with the count of changes it was caught up at, what each opened agent page showed, the usage it last fetched, and the changes to agents the server doesn't have yet in Expo's SQLite key-value store, through the store in `client/` that it shares with the desktop app. Those changes are laid over whatever the server sends until the server has them, so a reply arriving mid-change can't undo one. While open, it listens to `GET /events`. On launch and on returning from the background, where iOS drops the stream, it reconnects and catches up, fetching the newest page of only the chats that changed while it was away. Coming back from under Control Centre or the app switcher, it leaves a stream the server pinged lately as it is. A chat holds every page fetched of it while it is on screen, and goes back to its newest page when it is closed. The app keeps the server's address and the computer's name in the same store and its two keys in the Keychain, through `expo-secure-store`, in a group it shares with its notification extension. It sends the device key with every call, the event stream, and each avatar and attachment it loads. Until the phone has paired, welcome and pairing are its only screens. A 401 from the server clears the pairing and the saved chats, as Disconnect does once the server has forgotten the phone. The event stream reads the server's contract version each time it connects, and the home screen shows which side to update while they differ.

The app carries a demo computer for Apple's review (`mobile/src/lib/demo.ts`), since a reviewer has no computer of ours to pair with. It answers the calls the app makes to a paired computer, pairing and the event stream among them, with four made-up agents whose replies are written in the app, and serves the starter avatars and the pages two of the agents sent from the app's own files. Nothing sent to it leaves the phone, it sends no notifications, and it starts over when the app does. A phone reaches it only by the pairing link `sidebots://pair?host=demo.invalid&code=review`, which goes in the review notes. No screen leads to it, and the side menu names it "Demo computer". What it doesn't do, such as a fresh start, it refuses in words.

## Testing

The server is tested through its HTTP routes, with the runner swapped for a fake that returns set replies. That covers ordering, queuing, stopping, failure messages and the per-person filter without spending anyone's usage. The Codex driver is tested against a stand-in for Codex, `server/test/codex-peer.ts`, which answers its requests the way `codex app-server` does. The store in `client/` has unit tests of its own, and `docs/specs/2026-11-21-desktop-app.md` says how the desktop app is tested. One manual check per slice runs a real turn through the provider it touches. The app is checked in the iOS Simulator and then on a phone on mobile data. The relay's tests run the server's relay module against the relay's request handler, with Cloudflare's database and API and Apple's push service faked. A Live Activity is checked in the iOS Simulator for how it starts and looks, and on a phone for its end, which only Apple's push service delivers.

## Out of scope

- Live voice
- Chats shared between two people
- One build of the app shared by several households
- Agents that talk to other people's agents
- A Sidebots sign-in of its own, such as Google sign-in
- An Android build, and any client other than the phone app and the desktop app
- Driving websites that need a typed password
- Moving the server off the MacBook

## Work breakdown

Each slice ends with something that works on its own.

1. **One agent, no app.** Server, database, one agent folder, and the runner. Sending a message with `curl` returns a reply. This proves the subscription login, skills, connections and auto mode work through the SDK.
2. **Chat on the phone.** The server setup screen, the chat screen, the event stream, and Tailscale. A message typed on the phone gets a reply from the agent on the computer.
3. **Many agents.** The home screen, creating an agent from the plus button, avatars and the avatar picker, and identifying the person from their Tailscale login.
4. **Notifications.** Device registration and a notification when a reply lands.
5. **Attachments.** Sending a photo or file into the agent's folder.
6. **Memory and fresh start.** Memory files, replacing a session by hand and by size, and `search_history`.
7. **Making avatars.** An agent makes a new avatar with the `make-avatar` skill.
8. **Agents you can manage.** Jobs, the agent page, the model and effort, mute, hide and delete, replies to a message, and older messages.
9. **Second person.** A second config folder and Claude login on the server, a second Tailscale user, and the TestFlight build on both phones.
